## Problem

**Two problems in the same release tooling — a DRY problem and a hardening problem.**

### Problem A — the ship/strip partition is re-expressed by hand in ~7 places (DRY)

`build_release.py` `DEV_ONLY_FILES/DIRS` is the source of truth; it is then re-hand-partitioned three more ways in `check_shipped_content.py` (`_INIT_CREATES` · `HARNESS_SELF_SCRIPTS` · `_DANGLE_EXCLUDED`), echoed in the `init` managed-set table, and pinned again in `tests/test_build_release.py`. **Adding one dev-only doc that init recreates = 3–5 edits across 3–4 files** (0030 Slice 2 hit exactly this — `_CHARTER.md` needed the seed + the `_INIT_CREATES` entry + the test pin). Nothing cross-checks that `init` can actually (re)create everything the release strips — the release/init contract (`INVARIANTS.md`) is prose-only.

### Problem B — a BROKEN release can pass every gate today (hardening)

A verified release-pipeline audit found the publish path has holes a broken release slips through. The pipeline: `git pull --ff-only main` → `build_release.py --apply` (builds local `release`, strips dev-only, refuses a stale base) → manual `git range-diff` drop-check → manual `git push --force origin release` → marketplace `ref: "release"` (a mutable **BRANCH**, not a tag). The gaps:

- **No version-increase check.** `check_versions_synced.py` only asserts the two manifests AGREE (`plugin.json` ↔ `marketplace.json`) — never that the version moved off the last release. A forgotten bump ships a "new" release adopters see as no update. (Highest-probability silent bad release.)
- **The shipped tree runs ZERO CI.** `ci.yml` runs `on: [main]` only (`push`/`pull_request` → `branches: [main]`); the force-pushed `release` branch — what users actually install — is never CI-validated, and its commit is created with `--no-verify` (`build_release.py:198`). A break introduced by the strip transform is invisible until an adopter hits it.
- **No immutable rollback anchor.** The marketplace tracks a mutable branch; there is no `vX.Y.Z` tag to roll back to. This is precisely how the v0.1.40 distillation was lost (a stale-base rebuild + force-push, no tag to recover from).
- **The drop-check is a manual eyeball.** `git range-diff` (RELEASE_CHECKLIST.md:23-30) is the primary defense against a shipped file silently missing from the release — but it is model-upheld, not computed.
- **The force-push can silently clobber.** `git push --force origin release` overwrites `origin/release` unconditionally, even if it moved out from under the operator since fetch.
- **The stale-base guard misses a direct push.** `_dropped_merges()` (`build_release.py:149-160`) uses `rev-list --merges` — it only sees dropped *merge* commits, so a direct NON-merge push to `main` (which admin-bypass allows — see MEMORY: main branch-protection bypass) is invisible to it.

The hardening track adds guards so each of these becomes a loud, pre-publish failure instead of a post-publish surprise. **The additions naturally reuse the manifest's `classify()`** from the DRY track (the mechanized drop-check is a `classify()` subset assertion), so the two tracks compose.

### Problem C — the release is a convoluted, multi-step, hand-run checklist (consolidation)

Even with the DRY manifest and every guard in place, **releasing is still a hand-orchestrated sequence a human stitches together from `RELEASE_CHECKLIST.md`**: fetch → checkout+pull → **hand-edit `plugin.json`** → **hand-edit `marketplace.json`** to match → run the version-sync gate → run `build_release.py --apply` → eyeball its output → run the manual `git range-diff` drop-check → run `git push --force origin release` → `git tag …` → `git push origin vX.Y.Z` → maybe touch the marketplace. That is ~8–10 discrete manual steps, **two of them error-prone by-hand JSON edits that can silently drift** (the exact drift `check_versions_synced.py` exists to catch after the fact), and the guards from Problem B — if bolted on as independent scripts/checklist lines — would only *add* steps to that list. The maintainer's explicit direction: **"nicely formalise the release process and clean and tidy it up instead of the multiple hand-written and convoluted process it is now."** The fix is not more checklist entries — it is to **fold everything mechanizable into ONE deterministic entry point**, leaving the checklist a thin wrapper around a single command plus the one honestly-human decision (approve the irreversible push).

## Goals / Non-goals

The Slice-1 spec **maps every current `DEV_ONLY_FILES` entry to exactly one class** so the taxonomy is a provable *partition*, not a lossy re-encoding.
- **Goal:** Add the **referential-closure run-gate** (`NEEDS ⊆ HAS`): assert every stripped-adopter-relevant path is producible/recreatable. **Four HAS sources** (one per non-`config`/non-`dangle` class): `init-seed` → its `_X.md` seed ships; `init-gen` → a known init generator output; **`recreate-on-demand` → the class IS its own HAS attestation** (its members are *by design* not init-produced — the closure predicate accepts them via this class, it does NOT hard-require init-producibility for them); `self-gate` → the harness-self script's shipped/stripped status is self-consistent. This **mechanizes the INVARIANT** (`INVARIANTS.md:77-98`, prose-only today). The honesty copy says "producible by init **or the workflow's lazy/templated/agent authoring**" — never "producible by init" flatly (that would over-claim init's scope).
- **Goal:** **Provable no-op** — the shipped file set is **byte-identical before/after** (the load-bearing safety property; asserted by an equality check during migration).
- **Non-goal:** Folding `check_versions_synced.py` in — **it stays a SEPARATE gate** (verified: folding adds dual-manifest JSON parsing = scope creep + risk; the two-manifest agreement check is orthogonal). *(Corrects the dossier, which said "fold version-sync in.")*
- **Non-goal:** A version "third-drift-axis" detector — **REFUTED** (main + release both 0.3.1, in sync; the gate works as designed).
- **Non-goal:** Any adopter-facing change — this is internal harness tooling; adopters never see these scripts (all `DEV_ONLY`/stripped).

### Release-hardening goals (Track B — a broken release can't pass every gate)

Each guard converts a currently-silent bad outcome into a loud, pre-publish failure. Sized so each lands complete with a test.

- **Goal (P0-1, must-fix) — version-must-INCREASE guard.** Add a release-anchored check: read `plugin.json.version`, compare it to the version currently on `origin/release` (or the latest `vX.Y.Z` git tag), and **REFUSE if not strictly greater** (semver comparison). Lives in `build_release.py --apply` as a precondition (sibling to the existing stale-base refusal), *or* as a checklist-gated script — **decide at Spec** (prefer the `--apply` precondition so it can never be skipped, matching the stale-base guard's placement). Closes the highest-probability silent bad release (forgotten bump → adopters see no update). **This is distinct from `check_versions_synced.py`** (which checks the two manifests *agree*, an orthogonal axis) — do NOT fold the two together (see non-goal).
- **Goal (P0-2, must-fix) — validate the BUILT (stripped) tree before publishing.** Have `build_release.py --apply` run `check_shipped_content.py` + `pytest` (or a defined shipped subset) **against the throwaway built worktree** BEFORE it commits/finishes — so a break introduced by (or surviving) the strip transform fails loud pre-push rather than reaching an adopter. Closes the "release runs zero CI" hole. **Decide the exact validation set at Spec** (full `pytest` may reference dev-only `tests/` that the strip removes → run against the built tree only what remains meaningful there; the safe minimum is `check_shipped_content.py` on the built tree, which is already release-scoped, plus any shipped-subset tests that survive the strip).
- **Goal (P1-1) — tag each release** `vX.Y.Z` as an **immutable rollback anchor** (today the marketplace tracks a mutable branch — no rollback point; this is how a prior release was lost). The tag **doubles as P0-1's compare anchor**. **The tag is NOT created inside `--apply`** — it is emitted in the printed gated command (`git tag vX.Y.Z && git push --force-with-lease origin release && git push origin vX.Y.Z`) so it comes into existence only when the human publishes, leaving a declined/failed run with no dangling local tag that would corrupt the anchor / block a same-version retry (optionally a `gh release`). **MANDATORY release-prep bootstrap:** because the repo's tag history is incomplete — the latest `vX.Y.Z` tag is `v0.2.0` while the live shipped version is `0.3.1` (VERIFIED: tags are only `v0.1.0`/`v0.1.1`/`v0.2.0`; there is NO `v0.3.x` tag) — the very first action when this track lands is to **retroactively tag the current published release: `git tag v0.3.1 <the 0.3.1 release commit> && git push origin v0.3.1`** so the anchor equals the live version before P0-1's guard is ever trusted. Until that bootstrap tag exists, the guard's "max `vX.Y.Z` tag" anchor is *below reality* and would pass a downgrade to `0.3.0`. This is a **hard prerequisite of Slice 4 being trustworthy, not optional.** **Pointing the marketplace `ref` at the tag instead of the branch is a bigger call — NOTE it as an open question, do NOT do it in this plan.**
- **Goal (P1-2) — `--force-with-lease`.** Change the RELEASE_CHECKLIST's `git push --force origin release` to `git push --force-with-lease origin release` — refuses if `origin/release` moved out from under the operator since fetch, converting a silent clobber into a loud rejection. (Checklist copy only; no script.)
- **Goal (P1-3) — mechanize the drop-check.** Add a **computable** assertion to `build_release.py --apply` (reusing the manifest's `classify()`): the set of paths on `origin/main`-not-`release` must be a **SUBSET of the strip set** — so a *shipped* file accidentally missing from the release fails the build. Turns the manual `range-diff` eyeball into a machine check. (The manual `range-diff` stays in the checklist as defense-in-depth for what a path-set check can't see — commit-level drops.)
- **Goal (P2-2) — broaden the stale-base guard.** `_dropped_merges()` uses `rev-list --merges` (misses a direct non-merge push to `main`, which admin-bypass allows). Broaden to catch **any** commit on `origin/main` not reachable from `HEAD` — `rev-list origin/main --not HEAD` (drop `--merges`), or assert `HEAD` is an ancestor-inclusive match of `origin/main`. Rename/re-doc the function accordingly (`_dropped_merges` → `_dropped_commits` / `_missing_upstream_commits`).

### Consolidation goals (Track C — ONE release, ONE command, up to a single human-gated push)

The target shape: **one deterministic entry point runs every mechanizable step in order, up to (but not through) the one irreversible action.** The guards from Track B are not independent bolt-ons — they are the **validation stages of this single flow.** Prefer **extending `build_release.py --apply`** with a `--bump <version>` argument over introducing a new `release.py` (KISS/YAGNI — a new script is a second entry point to keep in sync; only split it out if a clear reason emerges at Spec).

**`python scripts/build_release.py --apply --bump <version>` runs, in ONE deterministic pass:**

1. **Preconditions (fail loud, before any mutation):** clean working tree · on the release-source branch (`main`) · ff-current with `origin/main` · the **broadened HEAD-ancestry / stale-base check** (Track B, P2-2). Any failure aborts with an actionable message before touching a file.
2. **Version bump from ONE arg:** `--bump 0.4.0` writes the version into **BOTH** `.claude-plugin/plugin.json` AND `.claude-plugin/marketplace.json` from the single value — so the two manifests **cannot drift** (this subsumes the two error-prone hand-edits from Problem C). If the manifests are already at `<version>` and in sync (e.g. a re-run after a failed push), **accept and continue** — do not refuse. `check_versions_synced.py` **stays** as the independent CI agreement gate (the `--bump` writer makes drift structurally hard *by construction*; the separate gate keeps the *independent* mechanical agreement check — belt and suspenders, orthogonal). `--bump` composes with the **version-must-INCREASE** guard (Track B, P0-1): the written version must be strictly greater than the latest `vX.Y.Z` tag, else abort.
3. **Build** the stripped `release` tree — the existing `_apply()` strip transform (unchanged behavior).
4. **Validate the built tree (Track B guards, now as stages of the one flow):** version-must-increase (tag-anchored, P0-1) · mechanized subset drop-check (`origin/main`-not-`HEAD` ⊆ strip-set, P1-3) · shipped-content on the **built** tree via `check_shipped_content.py --root <tmp>` (P0-2). Any failure aborts loud — no commit, no tag.
5. **Do NOT create the tag in-build.** `--apply` builds + validates + prints; it does **not** run `git tag`. The `vX.Y.Z` tag is created only as part of the printed gated command the human runs (step 6) — so no tag exists until the human commits to publishing, and a declined/failed/aborted run leaves ZERO side effects (no tag, no push). This keeps the version-increase anchor (Track B, P0-1) uncorrupted: the anchor is always the last *published* tag, never a dangling local one.
6. **STOP before the irreversible push** and **PRINT the exact single gated command the human runs:** `git tag vX.Y.Z && git push --force-with-lease origin release && git push origin vX.Y.Z` (Track B, P1-2 lease-safety) — tag-create + branch-push + tag-push are **one atomic human-gated step**, plus any marketplace-ref note. The force-push (and the tag it publishes) stays **HUMAN-GATED** — this is the one step that is honestly-not-automated; everything above it is one command, and the run is fully abortable with no side effects.

**`RELEASE_CHECKLIST.md` becomes a THIN wrapper**, not a hand-run list:
- (a) run `python scripts/build_release.py --apply --bump <version>`;
- (b) review its printed drop-check + validation summary;
- (c) run the one gated push command it prints;
- (d) update the marketplace `ref` only if the (deferred) repoint is ever done.
The convoluted manual step list is **removed/collapsed** — the checklist keeps ONLY the genuinely-human decisions: **approve the push**, and the **`[J]` eval-drift / `BASELINE.md` check** if still model-upheld.

- **Goal (C-1) — the `--bump` version-writer.** Add `--bump <version>` to `build_release.py --apply`: parse the version, write it to BOTH manifests via a **targeted version-field replacement** (regex/string replace of just the `"version": "X.Y.Z"` value in each of `plugin.json` + `marketplace.json` — both are 2-space-indented; **NOT** a `json.load`→`json.dumps` round-trip, which would reflow the whole file — e.g. `marketplace.json`'s long `description` string + nested `source` object — into a giant noisy diff and defeat clean human review) so the diff is **one line per file**, semver-validate it (well-formed + strictly greater than the latest tag, reusing P0-1's compare helper), accept a same-version no-op when already synced. Make the write **both-or-neither / partial-write-safe:** compute both replacements first and confirm both succeed before writing (or write-to-temp-then-rename per file), then immediately re-run `check_versions_synced.evaluate()` in-process and fail loud if the pair disagrees — a partial failure must never leave the two manifests drifted on disk (the clean-tree precondition already passed, so a half-write would make a *retry* abort at the clean-tree check with an uncommitted drift the operator must manually untangle). This is the single-source-of-truth bump — two hand-edits become one arg.
- **Goal (C-2) — orchestrate the guards as one flow.** Sequence the Track-B guards as the preconditions/validation-stages of `--apply --bump` in the run order above, so a release is **one command up to the human-gated push.** No guard is a separate script the operator must remember to run.
- **Goal (C-3) — the printed gated-command emission + thin-checklist rewrite.** On success, `_apply()` prints the exact `git tag vX.Y.Z && git push --force-with-lease origin release && git push origin vX.Y.Z` command (the operator copy-pastes the one human-gated step; the tag is *created* here, not in-build) plus the drop-check/validation summary. Rewrite `RELEASE_CHECKLIST.md` to the thin four-line wrapper above, collapsing the convoluted manual list and keeping only the human `[J]` decisions — the rewrite must be verified by an **explicit old-vs-new checklist diff** proving no genuinely-human step is silently dropped, specifically that the **`[J]` eval-drift / `BASELINE.md` check** and the manual **`git range-diff` defense-in-depth** survive the collapse.
- **Honesty (Track C):** the flow is **"one command up to a single human-gated push,"** NOT "fully automated." The force-push (irreversible) + the eval-drift `[J]` judgment stay human-gated; the checklist copy must state this split explicitly and never claim the release is fully automated.

### Hardening non-goals

- **Non-goal:** Repointing the marketplace `ref` from the `release` branch to the `vX.Y.Z` tag (P1-1's bigger call) — noted as an open question for a future plan; the tag ships as a rollback anchor + compare source now, nothing consumes it yet.
- **Non-goal:** A CHANGELOG. That is separate release hygiene, not this plan.
- **Non-goal:** Running CI *on the release branch* in GitHub Actions (adding `branches: [release]` to `ci.yml`). P0-2 validates the built tree **locally at build time** — pre-push, where the operator can act on a failure — rather than after the force-push. (Revisit only if local validation proves insufficient; YAGNI for now.)

### Consolidation non-goals (Track C)

- **Non-goal:** Automating the **force-push** itself. It is the one irreversible step and stays human-gated (`[J]`) — the flow STOPS and prints the command; it does not run it. This is the honest line: "one command up to a single human-gated push," never "fully automated release."
- **Non-goal:** A **new `release.py` script**. Prefer extending `build_release.py --apply` with `--bump` (KISS — one entry point, not two to keep in sync). Only introduce a separate orchestrator if a concrete reason surfaces at Spec (and record it in DECISIONS if so).
- **Non-goal:** A **marketplace-ref auto-repoint** (branch → `vX.Y.Z` tag). Stays a NOTED open question (P1-1's bigger call) — the flow prints a marketplace note but does not repoint; deferred to a future plan.
- **Non-goal:** **Folding `check_versions_synced.py`** into the flow. It stays a separate independent agreement gate — the `--bump` writer makes drift structurally hard *by construction*, but the orthogonal mechanical agreement check is deliberately kept as an independent CI gate (belt and suspenders; same rationale as the Track-A/Track-B version-sync non-goals).
- **Non-goal:** Automating the **eval-drift / `BASELINE.md`** judgment. It is model-upheld (`[J]`) and stays a human checklist decision — the flow does not run or gate on it.

## Approach

Migrate in **safety-netted steps, each green before the next** (the whole point is a provable no-op):
1. **Annotate** — convert `DEV_ONLY_FILES` into a `DEV_ONLY_PATH_CLASSES` dict (`path → class`, the **six** classes above); keep `DEV_ONLY_DIRS` (dirs stay out of the classes — the closure gate reasons over file-level classes only). Derive `is_dev_only()` / `classify()` / `recreate_class()` from the dict. **Map EVERY current `DEV_ONLY_FILES` entry to exactly one class** (the exhaustive partition — see the enumeration below) and **assert the shipped set is byte-identical** vs the pre-change `classify()` (the migration test). *(Enumeration: DECISIONS/ROADMAP/CHARTER→`init-seed` · ARCHITECTURE_TREE→`init-gen` · INVARIANTS/PRODUCT/PRODUCT_SPEC→`recreate-on-demand` · the harness-self scripts→`self-gate` · RELEASE_CHECKLIST→`dangle` · settings.json/CLAUDE.md/pyproject.toml/.gitignore/.gitattributes→`config`. Confirm the live list against `build_release.py` at Spec — the mapping is the partition-completeness check.)*
2. **Derive-alongside** — in `check_shipped_content.py`, compute `_INIT_CREATES` / `HARNESS_SELF_SCRIPTS` / `_DANGLE_EXCLUDED` from the class annotations, **alongside the old hand-lists**, and assert they're equal (the safety net). Keep both until equality holds.
3. **Delete** the three hand-lists once the derived sets prove equal.
4. **Closure check** — add `NEEDS ⊆ HAS` to `check_shipped_content.py`: derive `init_creates`/`recreate_on_demand`/`self_gates`/`dangle_set` from classes; assert every stripped-adopter-relevant path is recreatable via its class's HAS source (`init-seed`→seed ships · `init-gen`→init generator · **`recreate-on-demand`→the class itself is the attestation, NOT init-producibility** · `self-gate`→self-consistent ship/strip). **Honor the `INCLUDE_GLOBS` never-clobber carve-out** (the tree-script's glob assignment is adopter-owned — exclude it from closure exactly as init's body-compare does). May surface a real latent gap — good.
5. **Collapse the test pins** to `classify` + the closure assertion. **Migrate the `test_dangling_set_is_derived_and_excludes_gate_scripts` pin** (`tests/test_check_shipped_content.py`) so the derived dangle set still provably excludes the gate scripts — name it explicitly so Slice 2 lands complete, not with a silently-broken pin.

**`check_versions_synced.py` is untouched** (separate gate). The rename to `release_gate.py` (the dossier's naming) is **optional / deferred** — merging file names is cosmetic and risks churn; the value is the annotated manifest + closure check, which can live in the existing `check_shipped_content.py`. *(Confirm at Spec — prefer keeping the existing filename to minimize the DoD-gate-list / RELEASE_CHECKLIST / tree churn.)*

**Hardening + consolidation tracks (B + C) — approach.** The guards land AFTER the DRY track so P1-3's mechanized drop-check can reuse the finalized `classify()`. Each guard is its own slice with its own test. **They are built as the STAGES of the one `--apply --bump` flow, not as independent scripts/checklist lines** (Track C) — the run order is the flow order from the Consolidation goals: preconditions (P2-2 broadened stale-base) → `--bump` writes both manifests (C-1) → build → built-tree validation (P0-1 version-increase, P1-3 drop-check, P0-2 shipped-content-on-built-tree) → STOP + print the gated command (C-3), which emits the `vX.Y.Z` tag-create + `--force-with-lease` push as one atomic human-gated step (P1-1 — the tag is NOT created in-build). Build order to keep each slice safety-netted: the two **script-side must-fixes** (P0-1 version-increase precondition, P0-2 built-tree validation) land first as `--apply` stages; then the **guard broadeners** (P2-2 stale-base broadening, P1-3 mechanized drop-check) which both touch `build_release.py`'s pre-build assertions; then the **`--bump` writer + orchestration + thin-checklist/gated-command** slice (C-1/C-2/C-3) which wires the single entry point and rewrites `RELEASE_CHECKLIST.md`; the **tag + `--force-with-lease`** copy (P1-1, P1-2) folds into the flow's tag stage + printed command. Each script-side guard fails loud with an actionable message (matching the existing stale-base refusal's tone) and is unit-testable by driving `_apply()`'s stage helpers over fixture repos/refs — extend `tests/test_build_release.py`. **The `[J]`/model-upheld split is preserved:** the mechanical stages (version-increase, `--bump` dual-manifest write, built-tree validation, mechanized drop-check, broadened stale-base) fire in-build; the **tag-create + force-push** are emitted as the one printed gated command and stay model-upheld (so no tag exists until publish — an aborted run leaves zero side effects), as does eval-drift — the flow STOPS before the push and PRINTS the gated command, and the (now-thin) RELEASE_CHECKLIST copy must keep saying so and must not claim the release is "fully automated" or "fully enforced." ## Architecture & holistic fit

## Risks & mitigations

- **Risk: silently changing what ships.** → **Mitigation:** step-1 migration test asserts the shipped set is byte-identical to pre-change; the whole plan gates on that equality. If it differs, STOP.
- **Risk: the closure check surfaces a real latent gap and fails.** → **Mitigation:** that's a *good* find — fix the wiring (add the missing seed/managed-set entry) or the class annotation; do NOT weaken the check to pass.
- **Risk: the `INCLUDE_GLOBS` carve-out breaks closure** (the tree-script's glob line is adopter-owned). → **Mitigation:** exclude it from the closure NEEDS exactly as `init`'s body-compare does (recorded constraint).
- **Risk: scope creep (folding version-sync / renaming the file).** → **Mitigation:** explicit non-goal; version-sync stays separate; the rename is deferred/optional.

### Hardening risks

- **Risk: a hardening guard blocks a legitimate release** (e.g. version-increase compare mishandles the first-ever tag/branch, or a re-build at the same version during a hotfix). → **Mitigation:** define the missing-anchor behavior at Spec (first release with no `origin/release`/tag → allow, don't refuse); make refusals actionable and overridable only by fixing the cause, never by a silent bypass flag that becomes a footgun.
- **Risk: P0-2 built-tree validation is flaky or false-fails** because `pytest` references dev-only paths the strip removed. → **Mitigation:** decide the shipped-subset validation set at Spec; the safe floor is `check_shipped_content.py` on the built tree (already release-scoped); do NOT run the full dev suite against a tree that no longer contains `tests/`.
- **Risk: P1-3's path-set drop-check gives false confidence** (it catches a missing *shipped file* but not a dropped *commit* whose file also legitimately changed). → **Mitigation:** it is defense-in-depth, NOT a replacement — the manual `range-diff` stays in the checklist; the honesty copy must say the mechanized check is a subset guard, not a total drop guarantee.
- **Risk: over-claiming the release is now "safe."** → **Mitigation:** `honesty-reviewer` on the RELEASE_CHECKLIST copy; the guards reduce, never eliminate, risk — keep the existing "reduces, not eliminates" framing.

### Consolidation risks

- **Risk: over-claiming the release is "fully automated."** The single command mechanizes everything up to the push, but the force-push (irreversible) + eval-drift stay `[J]`. → **Mitigation:** `honesty-reviewer` on the flow + thin-checklist copy; the mandated framing is **"one command up to a single human-gated push"**; the flow STOPS and PRINTS the push command rather than running it — the honesty is structural, not just copy.
- **Risk: `--bump` writes one manifest but not the other (partial write) and leaves the pair drifted mid-run, on disk, in the dev tree** (and a *retry* then aborts at the clean-tree precondition on an uncommitted drift the operator must manually untangle). → **Mitigation:** compute both new file contents in memory first, confirm both targeted version-field replacements succeed, then write both (write-to-temp-then-rename per file, or at minimum write back-to-back) and immediately re-run `check_versions_synced.evaluate()` **in-process**, failing loud if the pair disagrees; on any write error leave a clear message that the tree may be half-written. The targeted-field replace (not a `json.dumps` round-trip) also keeps the diff one line per file. The existing clean-working-tree precondition + `check_versions_synced.py` as the independent post-gate are the belt-and-suspenders backstop.
- **Risk: collapsing the checklist DROPS a genuinely-human step** (e.g. the eval-drift `[J]` check, the `range-diff` defense-in-depth, or the marketplace note). → **Mitigation:** the thin wrapper explicitly RETAINS the `[J]` decisions (approve-push, eval-drift/`BASELINE.md`, marketplace note) AND the manual `git range-diff` drop-check (defense-in-depth — Slice 7's mechanized check is a *subset guard, not a total drop guarantee*, so it does not replace the eyeball) — the rewrite removes only the *mechanized* steps; `honesty-reviewer` + an **explicit old-vs-new checklist diff** confirms the `[J]` eval-drift/BASELINE step and the `range-diff` line are PRESERVED (not lost) and no human decision was silently laundered into apparent automation.
- **Risk: extending `--apply` arg-parsing (`"--apply" in argv`) with `--bump <value>` mishandles a missing/garbled value.** → **Mitigation:** validate the `--bump` value at the boundary (well-formed semver, present when required) and fail loud with an actionable message before any mutation; unit-test the arg-parse edges.
