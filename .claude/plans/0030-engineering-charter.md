## Problem

The harness **chooses its way of working per work-item — but it does so from tacit, unstated knowledge, with no explicit toolbox of established practices and no written statement of when each fits.** It already selects *some* discipline per work-TYPE (the tag→discipline table: `bug`→failing-test-first, `refactor`→characterization-first, `feature`→standard pipeline; standards are relevance-gated per change), so the *instinct* to fit the approach to the work is present — but coarse and implicit. Two concrete costs:

1. **The per-work choice isn't principled — it's ad hoc.** Because the toolbox of established practices (TDD, ATDD/BDD, DDD, trunk-based, contract-first, spec-by-example, GitFlow, Shape Up, …) and the "when does each fit" judgment live only in the model's tacit knowledge, the fit-to-the-work decision can't be reasoned about, reviewed, or made consistent across agents/sessions. There's no golden hammer today (good) — but there's also no written map of the tools and their fit, so the right-tool-for-the-work choice is invisible and unauditable.

2. **No per-project record of genuine preferences/deviations.** A project can't record "we prefer X here" or "we deviate from the default grain for this reason." Test discipline, slicing rhythm, branch model, and acceptance-criteria style default to the harness's grain (good) but a fresh agent resuming from the plan file + ledgers has no durable statement of any project-specific choice the team actually made — and no memory of *what approach it already chose for this kind of work last time*, so the same kind of work can be approached inconsistently across sessions.

**The charter is a LIVING, per-work-TYPE methodology record — not a static preferences sheet.** It maps **kind-of-work → chosen methodology + brief rationale**, and it GROWS as the project meets new kinds of work. Five behaviors:

- **RECORD** — the first time a kind of work comes up and the agent judges the fitting approach (from the toolbox), it writes that mapping to the charter (e.g. "feature / domain-logic → test-first, red-first via an independent test-author").
- **APPLY (consistency / standardization)** — when the same kind of work recurs, the agent reads the charter and continues with the recorded approach, so the project stays consistent across agents/sessions.
- **ADAPT (no golden hammer)** — a genuinely different work-nature in the same project is NOT forced into the recorded approach; the agent picks what fits *that* work from the toolbox and records THAT for its type.
- **GROW / LEARN** — the record accrues one entry per work-type over time and is REVISABLE: if a recorded approach proves wrong for that type, the agent updates it in place with rationale.
- **UPHOLD** — consistency WITHIN a work-type, adaptivity ACROSS work-types.

This applies to ANY methodology — TDD is only the running example. Concrete walk-through: the first domain-logic feature → the agent judges test-first fits → records it; the next same-kind feature → test-first applied per the record (consistency); a UI spike of a different nature → test-after fits → recorded for that type; back to domain-logic → test-first again per the record. Two guard-rails keep this honest and lean (see Approach): **record per work-TYPE, update-not-append** (one revisable entry per kind, never a per-work-item log — so the charter stays bounded under the doc-budget hygiene we just formalized), and **the record is a revisable DEFAULT, not a mandate** (the prior the agent starts from, always overridable with rationale that updates the record — so it learns/grows instead of ossifying into a golden hammer even within a type). It stays **MODEL-UPHELD** — recording is the existing "record decisions" discipline; **no PostToolUse / mechanical enforcement** (consistent with the whole layer staying model-driven).

**The point is methodology AWARENESS — a toolbox + when-each-fits — so the per-work choice becomes principled, never one golden hammer.** TDD is one tool in that toolbox (a good fit for logic-heavy / well-understood-requirements / bug / refactor work), applied WHEN it fits — never the flagship, never charter-enforced. The harness already embodies red-first for `bug`/`refactor` (`.claude/agents/implementer.md:17`) and is structurally ATDD (Stage-4 machine-readable acceptance criteria + Stage-7 runtime-QA-per-criterion + the "acceptance criteria met" DoD gate, `docs/claugentic-WORKFLOW.md:150`). The remaining refinement — making test-first available for `feature` work *when chosen* via an independent, clean-context test-author — is ONE option the toolbox offers, not a default that fires.

This is **already user-approved and diagnosed** (`docs/claugentic-DECISIONS.md` → *The workflow & roles*, 2026-06-29 v0.3 re-review; captured to ROADMAP, not built), with the 2026-07-03 course-correction that **TDD is not singled out**: the deliverable is the methodology-awareness layer, not a TDD mandate. This plan builds that.

## Goals / Non-goals

- **Goal (the heart):** Make the harness **METHODOLOGY-AWARE** — give it an explicit, written **toolbox of established practices AND when each fits**, so its existing per-work-item choice becomes principled, reviewable, and consistent instead of tacit. The natural home is a short **"choosing the approach for the work at hand — the methodology toolbox"** reference in `docs/claugentic-WORKFLOW.md`, sitting NEAR the existing tag→discipline table it extends. This LARGELY EXISTS coarsely already (the tag→discipline selection + relevance-gated standards) — the plan makes the awareness EXPLICIT, KISS, no new machinery.
- **Goal:** The toolbox covers the practices worth knowing and when they fit — **TDD** (logic-heavy / well-understood requirements / bug / refactor), **ATDD/BDD**, **DDD**, **trunk-based**, **XP**, **contract-first**, **CI/CD-gating**, **spec-by-example** (all embodied-or-accommodated by the harness today), plus **GitFlow** and **Shape Up** (opt-in WITH the honest against-the-grain caveat). No golden hammer: the agent picks per the NATURE OF THE WORK AT HAND, per work-item.
- **Goal:** An **OPTIONAL, LEAN engineering charter** — a **living, per-work-TYPE methodology record** (kind-of-work → chosen approach + brief rationale) that RECORDS the fitting approach the first time a kind of work arrives, APPLIES it when that kind recurs (consistency), ADAPTS for a genuinely different work-nature (no golden hammer), and GROWS/updates-in-place as the project learns — NOT a required "pick your methodology" gate. It is a LOCAL (never-managed, never-synced) file, sibling to `docs/claugentic-PRODUCT.md`. **An absent charter ≡ current (good) behavior**: every not-yet-recorded work-type defaults to the harness's grain (make-invalid-states-unrepresentable). Nothing in it is required; the record only fills as the project meets each kind of work, and each entry is a **revisable default, not a mandate** — recorded **per work-TYPE, update-not-append** (one bounded entry per kind, never a per-work-item log).
- **Goal:** Wire the **per-work methodology-selection** into `implementer` + `synthesizer-gate` so both consult the toolbox AND the charter record to pick the approach for the work-item at hand — an explicit extension of the tag→discipline selection — and so the record grows: **APPLY** an existing entry when this kind of work recurs (consistency), **RECORD** a new entry (with rationale) the first time a kind of work is judged, **ADAPT** for a genuinely different work-nature (no golden hammer), and **update an entry in place** if a recorded approach proves wrong (GROW). Consistency WITHIN a work-type, adaptivity ACROSS work-types — model-upheld, the existing "record decisions" discipline, no PostToolUse hook. The **independent, clean-context test-author** is the red-first *mechanism WHEN test-first is the chosen approach* — one option in the toolbox, wired so that when chosen it writes the failing tests first and the `implementer` greens them WITHOUT editing them.
- **Goal:** State the against-the-grain **honesty caveats** plainly (GitFlow long-lived branches · Shape Up fixed-appetite-variable-scope fight the harness's small-batch / fixed-quality-bar grain) — in the toolbox reference and echoed in the charter seed.

- **Non-goal:** **Singling out or enforcing TDD.** TDD is one tool among many, applied WHEN it fits, never the flagship, never charter-enforced. The plan must not frame test-first as a default or a required pick.
- **Non-goal:** A REQUIRED "pick your methodology" gate / a mandatory charter axis. Nothing in the charter is required; there is no "one axis you must pick." Every dimension defaults to the harness's grain; the charter records only genuine deviations.
- **Non-goal:** Any NEW mechanical gate/hook. The toolbox is **MODEL-UPHELD guidance, not a mechanical selector**; the red-first-when-chosen wiring stays **model-upheld** (implementer prompt + Verify gate — the same mechanism `bug`/`refactor` already use); mechanical enforcement waits for the **named-but-unbuilt** red-first/characterization `PreToolUse` hook (`docs/claugentic-DECISIONS.md` → *The deterministic gates* / the Trust-track item). **The plan must never claim enforcement before that hook lands** (honesty #1).
- **Non-goal:** A NEW standards module. Neither the toolbox nor the charter is a quality-catalog dimension — so nothing here touches `KNOWN_MODULES` in `engine/verify.js:57` or the `docs/claugentic-standards/` catalog (see Risks — this deliberately sidesteps that footgun).
- **Non-goal:** Imposing any methodology. GitFlow/Shape Up are pick-able with a caveat; nothing forces trunk-based or TDD or any other tool.
- **Non-goal:** A charter-editing command (no `/charter`). It is a plain text file the user edits directly + is offered at init (KISS — like `docs/claugentic-PRODUCT_SPEC.md`, which has no editor command either).
- **Non-goal:** The independent test-author as a NEW agent file. It reuses the existing spawn machinery (see Approach — a `general-purpose`/native clean-context spawn writing tests to a contract, NOT a new registered agent — sidesteps the plugin.json agents-registration footgun).
- **Non-goal:** Building the bootstrap-and-approve self-extension, JIT small-standards fills, or the kernel/domain-pack model (all separately ROADMAP'd; the charter is "methodology ⊂ software-pack" and the DECISIONS sequencing says build this FIRST).

## Approach

**Layer 1 (the heart) — the methodology toolbox lives in WORKFLOW, next to the tag→discipline table it extends.** Add a short **"choosing the approach for the work at hand — the methodology toolbox"** reference to `docs/claugentic-WORKFLOW.md`, sitting NEAR the existing tag→discipline table (section `:209`). It is a compact table/list: each established practice (TDD · ATDD/BDD · DDD · trunk-based · XP · contract-first · CI/CD-gating · spec-by-example · GitFlow · Shape Up) with a one-line **"fits when …"** and the harness's stance (embodied / accommodated / opt-in-with-caveat). This makes the *awareness* explicit — the agent's per-work choice is now made against a written map, not tacit knowledge. It EXTENDS the existing selection: the tag→discipline table already picks per work-TYPE (bug→failing-test-first, refactor→characterization-first, feature→standard); the toolbox reference makes the *reasoning* (which tool, why, for this work's nature) legible and adds the finer-grained tools. **MODEL-UPHELD guidance, not a mechanical selector** — no code reads it; the agent consults it.

- *Why in WORKFLOW, not a new doc?* WORKFLOW already owns the tag→discipline table and the DoD gate list — the toolbox is the same concern (how work gets done per its nature), so it belongs beside them (DRY, SRP, no new surface). A separate doc would fragment the ways-of-working truth.

**Layer 2 — the optional lean charter = a one-time-seed local file** (`docs/claugentic-CHARTER.md`) that is a **living, per-work-TYPE methodology record** — mapping *kind-of-work → chosen methodology + brief rationale*, recording genuine *preferences / deviations* from the harness's default per-work judgment AND the approach the project has settled on per work-type. It mirrors the established `_DECISIONS.md`/`_ROADMAP.md` one-time-seed convention exactly (`skills/init/SKILL.md` step 7): a shipped pristine `docs/claugentic-_CHARTER.md` that `init` copies → `docs/claugentic-CHARTER.md` (underscore stripped), **create-if-absent only, never refreshed, never stamped, kept OUT of the managed-set table** so the REFRESH upsert can never clobber a filled charter. **It is NOT a required "pick your methodology" gate** — the seed ships explaining "leave this empty and the harness uses its default per-work judgment; the record fills itself in as the project meets each kind of work." An empty/absent charter ≡ current (good) behavior. This is the cleanest fit for "durable, per-project, user-owned, never-synced, optional": the pattern, the guards, and the tests already exist — we extend a proven seam rather than invent a file class.

**Structure of the record — per-work-TYPE entries, update-not-append, defaults-to-grain, seed nearly empty.** The charter body is a short list of **one entry per kind of work** — each entry is `work-type → chosen approach + one-line rationale`, REVISED IN PLACE as the project learns (never a per-work-item append log — guard-rail #1: this is what keeps it bounded under the doc-budget hygiene). Each recorded approach is a **revisable DEFAULT, not a mandate** (guard-rail #2): it is the prior the agent starts from for that work-type, always overridable with rationale that then updates the entry — so the record LEARNS and GROWS rather than ossifying into a golden hammer even within a type. The seed ships **nearly empty**: the prose header + a couple of illustrative (commented / example) rows showing the `work-type → approach + why` shape, so the record accretes RECORD-by-RECORD as real work arrives rather than being pre-filled. Every work-type not yet recorded silently defaults to the harness's grain (the WORKFLOW toolbox judgment).

- *Why not a managed/refreshed doc (like WORKFLOW)?* A managed doc is source=ship=refreshed-on-re-init — the exact opposite of "records the per-project deviation." Rejected.
- *Why not a section inside CLAUDE.md's managed fence?* The fence is byte-identical-every-run managed content; per-project choices can't live inside it. A charter *pointer* can sit in the fence (see Slice 2), but the choices live in their own local file.
- *Why not fold into `docs/claugentic-PRODUCT.md`?* PRODUCT.md is product/UX truth (who-for, JTBD, design language); the charter is *engineering methodology* truth. Different concern, different reader (`product-designer` vs `implementer`/`synthesizer-gate`) — SRP says separate file, sibling not merged.
- *Why not `CLAUDE.local.md`?* That is the solo-mode local anchor; the charter is a **shared-by-default** team artifact (the team's ways-of-working). It commits in shared mode (like PRODUCT.md), goes local only under the existing solo-mode `.git/info/exclude` routing.

**The charter is a growing per-work-type record, defaults-to-grain — no required axis.** The seed ships as a nearly-empty template: a short prose header ("the harness picks the approach per work-item from its toolbox; this record captures the approach chosen per kind of work as the project meets each one — RECORD when a new kind arrives, APPLY the recorded approach when it recurs, ADAPT for a genuinely different work-nature, and update an entry in place if a recorded approach proves wrong") plus one or two *illustrative example* entries in the `work-type → chosen approach + one-line rationale` shape (e.g. "feature / domain-logic → test-first · logic-heavy, well-understood requirements") each stamped "default: the harness's grain (see WORKFLOW toolbox) — a revisable default, not a mandate." Nothing is required; every not-yet-recorded work-type silently keeps the default. This is the standards-module JIT discipline applied to methodology: an entry "appears only when the project actually meets that kind of work" — grown, per work-type, update-not-append.

**The red-first mechanism WHEN test-first is chosen = an independent test-author** wired through the existing spawn machinery, not a new agent — **one option in the toolbox, not a default.** When the per-work choice selects test-first for a feature area — whether freshly judged from the toolbox (then RECORDED to the charter for that work-type) or APPLIED from an existing charter entry for that work-type — the `implementer` slice runs in two clean-context phases: (1) a **test-author spawn** (clean context, given only the slice's spec + acceptance criteria, NEVER the implementation plan's solution) writes the failing tests and confirms they fail; (2) the `implementer` greens them **without editing the test files** (structural integrity a human team can't self-enforce — the value is higher for an agent than a human, per DECISIONS). This is **ENCOURAGED when chosen** (implementer prompt + Verify gate); enforcement waits for the unbuilt PreToolUse hook. When test-first is NOT the fitting approach for this work-type (a recorded or freshly-judged different approach — ADAPT, no golden hammer), this path simply doesn't fire — the default feature build is unchanged.

**The honesty caveats** live in both the WORKFLOW toolbox reference and the seed's prose: each against-the-grain practice (GitFlow · Shape Up) carries a plain one-line "this works against the harness's small-batch / fixed-quality-bar grain because …" so the harness never silently "supports" a practice the pipeline half-fights.

## Architecture & holistic fit

**Codebase fit.** The deliverable is two thin layers of *documentation + read-first wiring*, no new machinery: (1) the **methodology toolbox reference** — MODEL-UPHELD guidance authored into `docs/claugentic-WORKFLOW.md` beside the tag→discipline table; (2) the **optional charter** — a local project-memory doc in the same family as `docs/claugentic-PRODUCT.md` (durable product context) and `docs/claugentic-DECISIONS.md`/`ROADMAP.md` (project ledgers). It rides four established seams with **zero new machinery**:
- **The WORKFLOW-authoring seam** (the tag→discipline table + DoD gate list already live in `docs/claugentic-WORKFLOW.md`): the toolbox reference is authored beside them — the same ways-of-working concern, so no new doc/surface. Model-upheld guidance; nothing reads it programmatically.
- **The one-time-seed seam** (`skills/init/SKILL.md` step 7 + the `_X.md`→`X.md` convention + `scripts/build_release.py`'s **default-include** classify + `tests/test_build_release.py`): a shipped pristine `_CHARTER.md`, copied create-if-absent, never refreshed, out of the managed-set table. **`build_release.py` needs no edit** — its classify ships everything not in `DEV_ONLY_FILES`, and the seed is deliberately NOT dev-only (same as `_DECISIONS.md`/`_ROADMAP.md`); the only build-contract work is a `tests/test_build_release.py` pin. Layering: the charter is *adopter-owned content*, not *managed harness content* — the same side of the line as a filled DECISIONS ledger.
- **The agent Read-first seam** (`implementer.md` + `synthesizer-gate.md` already open CLAUDE.md / WORKFLOW / ARCHITECTURE_TREE / in-scope standards): they already read WORKFLOW (so the toolbox reference is picked up for free); add the *optional* charter record to their read-first list — a pointer, self-contained (agents can't follow links at spawn, so the instruction is inline, mirroring how the DoD list is duplicated into builder/verifier agents — controlled, not drift). The read-first instruction says "consult the WORKFLOW toolbox AND the charter record to fit the approach to this work — APPLY the recorded entry for this work-type, else RECORD what you judge; ADAPT for a genuinely different work-nature; update an entry in place if it proves wrong." Recording/updating is the existing "record decisions" discipline (model-upheld, update-not-append), NOT a new mechanical write.
- **The Stage-6/Stage-7 spawn seam** (native implement + `engine/verify.js` fan-out): the test-author is a clean-context spawn to a contract — the same *structural-independence* posture the gate/refute roles already use, reused for test-authoring **when test-first is the chosen approach**. **No new engine args-contract field** (KISS — the orchestrator passes the red-first instruction + the job into the existing prompt, exactly as the whole-feature closing pass passes the Stage-1 JTBD without a new engine field, `docs/claugentic-WORKFLOW.md:103`).

**SOLID / separation-of-concerns.** SRP: the WORKFLOW toolbox owns *methodology-awareness* (which tool fits which work) beside the tag→discipline table it extends; the charter file owns *per-project, per-work-type chosen-approach truth* (the living record — distinct from PRODUCT.md's *product truth* and CLAUDE.md's *structural truth*). DRY: the "when each fits" judgment lives in ONE place (the WORKFLOW toolbox); the charter record points at it rather than restating it, and defaults-to-grain rather than re-declaring the grain; update-not-append keeps one entry per work-type (no duplicated-per-item state). DIP: both layers are passive records the agents *read* (and grow) — they invert no control, add no runtime dependency, and an empty charter degrades gracefully to all-defaults (make-invalid-states-unrepresentable). No golden hammer: selection is per-work — APPLY within a work-type, ADAPT across work-types.

**Product fit.** Serves the harness user (`docs/claugentic-PRODUCT.md` → the capable non-engineer) two ways: the toolbox makes the harness's per-work approach-choice **legible** ("here's the practice I'm using and why it fits this work"), and the optional charter lets a project **record a genuine preference once, in plain English, and have every agent honor it** — without forcing anyone to "pick a methodology." This reinforces the "in control, never surprised" design language: the reasoning is visible and the deviation is recorded, not re-litigated per plan. The charter is optional and defaults-safe; the against-the-grain caveats keep the surface honest (never silently "support" a fought practice).

**Quality dimensions to uphold** — the relevant subset, each mapped to its real `docs/claugentic-standards/` module (the forward-pointer the Spec's per-slice *in-scope dimensions* refines):
- **`docs-traceability`** — the toolbox reference and the charter are both traceability docs; the ARCHITECTURE_TREE entry, the DECISIONS entry, and the clarity of the WORKFLOW toolbox + seed are the bar. (Primary dimension for slices 1, 2, 4.)
- **`testing`** — the red-first-when-chosen wiring is a test-strategy change; the independent-test-author contract and the "greens without editing tests" rule are audited here. (Primary for slice 3.)
- **`maintainability-structure`** — SRP of the WORKFLOW toolbox vs the tag→discipline table, and the charter file vs PRODUCT.md/CLAUDE.md; DRY of the defaults; no dead config; the KISS "no new command / no new agent / no new engine field / no new doc" guardrails. (Cross-cutting all slices; `yagni-sentinel` guards the over-confine / over-build edge — the stated risk.)
- **`product-ux`** (plain-English surface) — the toolbox copy + the optional-charter framing honor the design language (plain-English-first, honest-by-construction, never a forced pick). (Slices 1, 2, 4.)

**Future-proofing (kept open, NOT built now — YAGNI).** The WORKFLOW toolbox is the natural growth point for the **methodology-slot of the kernel/domain-pack model** (DECISIONS: "charter = methodology ⊂ domain-pack") — a new practice is a new line, no machinery. The charter's per-work-type record is likewise extensible (a new kind of work is a new entry, authored by the agent when it first arrives — update-not-append). When the red-first/characterization **PreToolUse hook** lands, it can read the SAME charter record this plan writes — so this plan sets the record the future hook could honor, without pre-building the hook or claiming it. Optional-and-grown-per-work-type means both layers grow per real need, never speculatively (the standards-module JIT pattern). **Do not** build an axis-validation schema, a charter linter, a mechanical toolbox-selector, or a `/charter` command now — none is asked for.

## Risks & mitigations

- **Singling out / imposing a methodology (the STATED risk — "one theory, not the golden hammer").** Framing TDD as the flagship, or making the charter a required "pick your methodology" gate, would break the no-golden-hammer / universal-harness constraint. **Mitigation:** the toolbox is a *menu of tools with when-each-fits*, chosen per-work; TDD is one entry among many, applied only when it fits. The charter is OPTIONAL and grows per-work-type — **nothing in it is required**; every not-yet-recorded work-type defaults to the harness's grain, so an empty/absent charter ≡ current behavior; and each recorded entry is a **revisable default, not a mandate** (guard-rail #2), so a genuinely different work-nature is ADAPTED to, never forced into a recorded approach — the record can't ossify into a golden hammer even within a type. `yagni-sentinel` + `honesty-reviewer` on the Stage-2b panel and at Verify guard the over-confine / over-impose edge. The toolbox and charter INFORM and RECORD, never IMPOSE.
- **Over-confining a universal harness / unbounded growth (keep it lean).** A fat charter that forces choices, or a record that appends a line per work-item, would break the universal-harness constraint and the doc-budget hygiene. **Mitigation:** the charter ships nearly empty (prose header + one or two illustrative example rows); an entry "appears only when the project actually meets that kind of work" (the standards-module JIT discipline); and it is recorded **per work-TYPE, update-not-append** (guard-rail #1) — one bounded, revised-in-place entry per kind, never a per-work-item log — so it stays lean under the same doc-budget hygiene we just formalized. The toolbox lives as reference in WORKFLOW, not a runtime gate.
- **Over-claiming enforcement (honesty #1).** Copy that says the toolbox *selects* mechanically, or that test-first-when-chosen is *enforced*, would be a lie until the PreToolUse hook lands. **Mitigation:** the toolbox is stated **MODEL-UPHELD guidance, not a mechanical selector**; all red-first-when-chosen copy says **"encouraged / model-upheld"**; the honesty-reviewer is on the Stage-2b + Verify panels (trust surface); the plan and every artifact state enforcement waits for the named-but-unbuilt hook.
