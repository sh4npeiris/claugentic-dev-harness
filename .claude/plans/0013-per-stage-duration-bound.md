## Problem

`workflows/build-item.js` iterates `implement → gates → verify → QA → fix` until green or the iteration/budget cap. Two stages shell out to **arbitrary repo commands**:
- **gates** — `gatesPrompt` (build-item.js:501-511) tells an agent to run every `repo.gateCommands` entry (e.g. `pytest`, `node --test`, the gate scripts).
- **implement/fix** — the `implementer-architect` agent (build-item.js:591) may run build/test commands.

Any of those can run far too long: a hanging test, a blocking dev-server left in the foreground, an infinite loop in the code under test. Today there is an *implicit* backstop — the Bash tool's own **120s default timeout** — but it is the wrong safety contract for an unwatched run on **both** ends:
- **Too weak / discretionary** — the default is agent-discretionary: a stage agent can pass a longer timeout (up to 600s), background a process (which escapes the per-call bound entirely), or wait on a tool that escapes the per-call default. An unwatched run's termination guarantee must not rest on each agent's discretion. The existing caps bound the **number** of iterations (`maxIterationsFor`, `budget.agents`), **not the duration of any single stage**.
- **Too short** — a legitimately slow gate suite (>120s) spuriously fails the unconfigurable tool default.

So the gap is the absence of an **explicit, per-repo-configurable per-stage bound** — one the contract states (not an implicit default), a slow repo can raise (up to the Bash 600s hard max) and a fast repo can tighten. The bound is **fail-closed where a mechanical consumer exists** (gates' red decision on the reported exit code; qaBoot's clamp) and an **explicit standing instruction where none does** (implement/fix) — the strongest available register per stage, **not** a uniform deterministic resolution (see the three-way register in Goals).

Scope note: the **QA boot is already explicitly bounded** — `qa.js` clamps `readinessTimeoutSec` (default 60s, cap 300s; qa.js:96-97, 189-199) and probes on a bounded `readinessPlan`, so a boot that never comes up already fails closed. The genuine **net-new** work is therefore **gates + implement/fix**; for QA this plan only makes the existing boot bound configurable *from the engine* (qa.js stays the default-and-clamp owner).

## Goals / Non-goals

- **Goal:** an explicit, per-repo-configurable **per-command** duration bound on the stages that run arbitrary repo commands (**gates**, **implement/fix**), keyed per-stage with distinct defaults.
- **Goal:** thread the **already-existing** QA-boot bound (`qa.js` readiness) through the engine as a per-repo-configurable value — **pass-through-when-set only**, so `qa.js` stays the sole default-and-clamp owner and no `300`/`60` constant is duplicated into this script (DRY).
- **Goal:** **honest, three-way enforcement register** (the load-bearing honesty content — see Approach). The three bounded stages do NOT enforce equally, and the contract must say so:
  - **gates** — agent-instructed per-command timeout **+ a mechanical red decision** (`gatesGreen` reads the reported exit code; a timeout → 124 → red). Strongest.
  - **qaBoot** — a **mechanical clamp** in `qa.js` (`parseRunArgs` `Math.min`, qa.js:189-199) + an agent-executed *bounded* readiness probe (`readinessPlan`). Mechanical bound, agent-executed probe.
  - **implement/fix** — an **instruction-only** anti-hang nudge: `IMPLEMENT_SCHEMA` has **no exit-code channel** (build-item.js:408-437), so there is no mechanical consumer; a runaway surfaces downstream via the gates stage + the iteration cap. Model-upheld end to end. Weakest — and the SKILL/header copy must not launder it into the gates-strength claim.
- **Goal:** state plainly that the bound is **per-command, agent-enforced at the Bash-tool layer**, never a hard wall-clock stage-kill; the verbatim green close-out register is **unchanged**.
- **Non-goal:** a hard wall-clock kill of a pure-reasoning agent loop or a stage total — **impossible in-sandbox** (no clock). That residual is only **indirectly mitigated** — the platform's agent-turn limits and the iteration/budget cap bound *call counts*, not wall-clock; **no mechanism in this plan bounds a stage's total duration**.
- **Non-goal:** bounding `qa.js`'s flow-driving (Playwright/HTTP after boot) — `qa.js`-internal; the drivers carry their own tool timeouts. A dedicated bound there is a separate item if a real hang surfaces.
- **Non-goal:** touching the **verify** stage (read-only diff reasoning, no long Bash) or the cross-script-pinned `MODELS`/`SAME_MODEL_TAG`/`UNRESOLVED_FAMILY_TAG`/`KNOWN_FAMILIES`/`modelFamily`/`sameModelTag`/`parseArgs` block.

## Approach

**The forced constraint.** `build-item.js` runs in the Workflow sandbox with **no wall-clock** (header lines 22-23; `Date.now()` throws). The script itself cannot time a stage. The only place wall-clock actually elapses is **inside the Bash commands the stage agents run**, and the **Bash tool's `timeout` parameter** (ms, hard max 600000 = 600s) is the one cross-platform lever. A shell `timeout(1)` is at most a POSIX-only fallback — Windows `timeout.exe` is a *delay*, not a process bound, and this repo CIs on Windows, so the contract mandates the **tool parameter**, never a shell `timeout` command.

For the **gates** stage this composes with the existing fail-closed logic: the gates agent already returns a structured exit code per command (`GATES_SCHEMA`), and `gatesGreen` treats any non-zero (and any missing/non-numeric) exit as red (build-item.js:238-253). A timed-out command observes **no** real exit code, so the prompt names **124 as the timeout convention** (the one allowed non-observed code, with the timeout noted in `outputTail`) — reconciling with `gatesPrompt`'s standing "the ACTUAL process exit code … never an opinion" rule (build-item.js:507-509): 124 is a *named convention for a no-exit-observed timeout*, not an opinion about pass/fail.

**The design.**
1. New optional arg **`caps.stageTimeouts`** = `{ implement?, gates?, qaBoot? }` (positive integers, seconds; all keys optional). `validateArgs` fails loud on: a non-object `stageTimeouts`, **any unknown key** (exact-key set — match the frozen-criterion precedent at build-item.js:149-154, so a typo'd `qaboot`/`implment` can't silently fall back to default), a non-integer or ≤0 value, or a value > `MAX_STAGE_TIMEOUT_SEC` (600 — the Bash-tool hard max; a "configurable 800" that can't be honored is rejected, not silently clamped — fail-loud register).
2. A pure helper **`resolveStageTimeouts(caps)`** → `{ implement, gates, qaBoot }`, applying **per-stage distinct defaults** (`DEFAULT_STAGE_TIMEOUTS = { implement: 600, gates: 600, qaBoot: null }`). `implement`/`gates` default to `MAX_STAGE_TIMEOUT_SEC`; **`qaBoot` has NO engine default (`null` = not set)** — `qa.js` owns the default(60)/clamp(300). No clamping here (the boundary already rejected out-of-range values); `MAX_STAGE_TIMEOUT_SEC` is the single ceiling constant, referenced not duplicated.
3. **Thread** the resolved bounds (each stage per the three-way register):
   - `gatesPrompt(repo, branch, worktreePath, gatesTimeoutSec)` — instruct: run each command via the **Bash tool's `timeout` parameter** set to `<gatesTimeoutSec>`s; a command that hits it is a **FAILURE** → report `exitCode` 124 (the named timeout convention) with the timeout noted in `outputTail`. **Per-command**, not a stage total. → mechanical red via `gatesGreen`.
   - `implementPrompt(item, repo, residual, branch, implementTimeoutSec)` — standing rule: bound any long-running command with the Bash tool's `timeout` (≤ `<implementTimeoutSec>`s); on exceed, treat as failure and report — never hang. **Instruction-only** (no exit-code channel; honest anti-hang nudge, surfaces downstream).
   - `qaChildArgs(item, repo, criteria, builderFamily, iteration, qaBoot)` — a **new pure builder** for the QA child-workflow args (extracted from the inline object at build-item.js:719-728 so the threading is *unit-testable*, consistent with the relocation rationale): includes `readinessTimeoutSec: qaBoot` **only when `qaBoot != null`** (pass-through-when-set; absent → `qa.js`'s own 60s default). `qa.js` `Math.min`-clamps to its 300s cap (silently at runtime, qa.js:199) — the SKILL documents the clamp (qa.js stays the 300 owner), so the *contract* isn't silent even though the runtime is.
4. **Testability:** relocate `implementPrompt` + `gatesPrompt` (already pure string builders, build-item.js:465-511, no tool-primitive closure) and add `qaChildArgs` **into the `// --- helpers ---` block** — matching the `audit.js` precedent (`buildLensPrompt` et al. in-block, unit-tested) — so all three threading seams are covered. (Bounded: only these builders; **not** qa.js's QA prompt-builders — that is the separate Tier-1 backlog item.)
5. **Honesty:** a header note + a one-line comment at the resolve site carrying the **three-way enforcement register** + the **per-command (not stage-total)** semantics + the **>600s single-command residual** (a legitimate single command exceeding 600s can't be bounded-and-completed in one foreground call — split the suite or it isn't bounded-runnable); `SKILL.md`'s `caps` contract carries the same caveats; the verbatim green close-out register is **unchanged**.

**Alternatives rejected:**
- *Script-level wall-clock timing* — impossible (no clock in-sandbox).
- *Orchestrator/skill-level stage kill* — the skill invokes one `workflow()` call and gets the result; it cannot interrupt a stage mid-flight without the platform exposing per-stage cancellation (it does not). Agent-Bash-tool-layer is the only lever available today.
- *A single global `perStageTimeoutSec`* — rejected per the approved decision (per-stage distinct defaults: a build suite and a boot probe have very different legitimate durations).
- *`qaBoot` defaulting to 300 in this script* — rejected (duplicates `qa.js`'s `READINESS_TIMEOUT_CAP_SEC` and silently shifts the engine's boot default 60s→300s); pass-through-when-set keeps `qa.js` the sole owner.

## Risks & mitigations

- **Over-claiming a mechanical guarantee / laundering the implement nudge into the gates-strength claim** (the central risk) → the explicit **three-way enforcement register** in header + SKILL; green close-out register unchanged; **honesty-reviewer** convened at Plan (this revision) and in the Verify panel (trust surface).
- **The per-command bound read as a stage total** → header + SKILL state per-command explicitly; the >600s single-command residual named (split the suite or it isn't bounded-runnable).
- **The Windows `timeout.exe` trap** → the contract mandates the **Bash tool's `timeout` parameter**, never a shell `timeout` command; the prompt wording is asserted by the `gatesPrompt`/`implementPrompt` unit tests.
- **Breaking the cross-script drift pin** → the new helpers are build-item-local; the pinned block is untouched; `cross-script.test.mjs` stays green (re-run it).
- **A legitimately slow gate suite hitting the bound** → configurable per-repo via `caps.stageTimeouts.gates` up to 600s; default is the 600s max (loosest safe), documented in SKILL.
- **Relocating the prompt builders / extracting `qaChildArgs`** could change behavior → pure moves/extractions (no logic change); existing call sites pass the same values; all 319 existing node tests must stay green.
