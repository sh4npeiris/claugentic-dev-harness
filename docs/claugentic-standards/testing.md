# Testing — does the suite actually prove the behavior, and will it catch the next regression?

> **Loads when:** any change that adds, edits, or deletes tests; any behavior change that *should* be tested; refactors of legacy/untested code (characterization first); UI work (visual + a11y); flaky-test triage; or coverage/CI-gate changes.
> **ISO/IEC 25010:** Maintainability (testability, analysability, modifiability) with Reliability and Functional-suitability — tests are the safety net every other dimension leans on. · **Status:** draft
> Method, tags, honesty register: `README.md` → *Reading a module*.
> **Governing rule across every dimension: trust the oracle, not the author's word.** "Tests pass" is necessary, never sufficient — the audit asks *what would have to break for this test to fail?*

---

## Test pyramid (shape of the suite: unit / integration / e2e)

- **Auditor checks —** `[J]` Is each new behavior tested at the cheapest level that proves it, or pushed up into a slow/broad test out of convenience? `[J]` Is there an inverted pyramid (many e2e, few unit) signalling untestable design? `[D]` Test-suite wall-clock time and per-tier counts (where the runner reports tiers/tags). `[J]` Do integration tests exercise the *real* seam (DB, serialization, HTTP contract) rather than mocking the very thing under test?

## Characterization tests & golden master (the equivalence oracle for legacy refactors)

- **Auditor checks —** `[J]` Does a non-trivial refactor of previously-untested code introduce characterization/approval tests *before* the change (visible in commit order or PR narrative)? `[J]` Do they capture *actual* behavior (including known-quirky/buggy output) rather than asserting idealized behavior? `[D]` Golden-master baseline files are committed, diffable, and regenerable by a documented command. `[J]` Once the code is understood, are throwaway characterization tests promoted to intent-revealing tests or kept deliberately?

## Mutation testing (are the tests real?)

- **Auditor checks —** `[D]` Mutation run on the changed critical module; score meets the agreed threshold (e.g. ≥80% on core logic). `[J]` Are surviving mutants triaged (genuine gap → add assertion; equivalent → justified suppression) rather than blanket-ignored? `[J]` Is the tool aimed at logic that matters, not vanity-run across trivial code? `[D]` Mutation config/CI step present where the team has adopted it. `[J]` For each **named central claim** in the diff (a test whose *name* asserts a structural property — "anchored to `__file__`, not the cwd" · "capped" · "byte-identical"), construct the exact wrong implementation the claim forbids and **run it**: does the suite go red? Four vacuity shapes recur — the test **recomputes the implementation's own expression** on both sides, or compares the implementation's output to the implementation's **own exported constant** (a tautology; the remedy is an **independent literal** written out in the test, so a swapped, dropped, reordered or added element is a diff — 0041 S10a: a default review-panel set was "pinned" only against itself, and all four of those mutants survived); the **ambient environment makes right and wrong coincide** (the suite runs from the one cwd / locale / timezone / **working-tree shape** where both agree — run the mutant in the shape the defect *inhabits*, not the shape you happen to be standing in); and the pin **exercises a regime where the mechanism is inactive** (an overflow guard pinned only on inputs that never overflow); and the **corpus already satisfies the assertion elsewhere** — the artifact under test contains the asserted string twice, so the mutant's target was never the only source (see *Declarative artifacts* below for the anchoring technique). `[J]` Is a boundary pinned from **both** sides (`n-1`, `n`, `n+1`) against a **fixed** reference, or from one side only — where `>` vs `>=` *and* a changed threshold both survive?
- **Incident —** 0041 S3 (2026-08-13), three load-bearing pins that asserted nothing, and the fix each needed. A `__file__`-vs-cwd pin **recomputed its own expression**, and pytest runs from the root where both coincide → killed by spawning the module in a subprocess with `cwd=tmp_path` holding a **decoy** manifest. A 30-day boundary was fed boundary **+5s**, so `>`→`>=`, `30`→`7` and `abs()` all survived → killed by a `(29,F) (30,F) (31,T) (-31,F)` table against a **fixed** `now`. A “byte-identical” promise was pinned only where the reserve mechanism never bites. In the same review a genuinely **equivalent** mutant (`.isdecimal()`→`.isdigit()`, subsumed by a `try`) was proven so over all 1,114,112 code points and **left in place with the proof and the killable half named in the docstring** — the right disposition for an unkillable mutant.

## Declarative artifacts (CI workflows, manifests, config — and instruction files a human or agent executes) — assert the refusal, not the vocabulary

- **Good looks like —** Parse the artifact with a real parser; **scope** each assertion to the unit that owns the behavior (job · step · key); assert the **refusal or effect** (the `exit 1`, the `needs:` edge, the denied permission), never that a keyword appears somewhere. Cross-artifact parity is **derived** as a set relation plus an explicit floor, never a hand-typed list. **This dimension owns the anchoring technique** for an instruction artifact with no parser (a runbook, a prompt/skill file, a template an agent executes): assert the anchor occurs **exactly once**, split on it, assert **inside that slice** — never an ordinal index, never the whole file. Fixtures are **extracted from the artifact's own bytes**; a hand-transcribed copy tests your reading of the prose, not the prose.
- **Auditor checks —** `[D]` Delete the guard clause the test names and re-run: does the suite go red? (a whole-file substring assertion survives, because a neighbouring `echo`, comment or error message still carries the string). `[J]` Is each assertion anchored to its owning job/step/key, or does it search the parsed document globally? `[J]` Does the test assert the artifact *refuses* the bad case, or only that it *mentions* the check? `[D]` Is the artifact parsed (YAML/JSON/TOML) rather than string-matched, so a shape break fails loud in the suite rather than silently at runtime? `[J]` Is a parity list between two artifacts derived, or hand-maintained? `[D]` Count the asserted literal's occurrences **in the artifact itself**: more than one and a whole-file assertion is vacuous *by construction* — region-scope it, then re-run the deletion mutant. `[D]` Is every fixture for an instruction artifact derived from that artifact (extracted/parsed), or hand-transcribed?
- **Incident —** Three, same repo. (1) `/build` and `/condense` shipped across v0.4.0–v0.5.1 with **unparseable YAML frontmatter** — three releases loading with empty metadata, because nothing parsed them. (2) 0041 S2 (2026-08-12): a hand sweep of **13 mutants left 9 alive** — deleting a lease comparison *and its `exit 1`*, and deleting the tag↔manifest refusal, each left the suite 26/26 green because a surviving `echo` in an adjacent step carried every asserted string; fixed by a `_step_run(job, name_fragment)` helper that fails loud on 0-or-2 matches, and a hand-typed parity list became `gate_scripts(ci) ⊆ gate_scripts(release)` plus a floor. (3) 0041 S7 (2026-08-16), the same defect **twice in one slice, the second inside the fix for the first**: a whole-file substring pinned a path occurring eight times in that file, so deleting the slice's headline row left all 638 tests green; the region-scoped fix (`text.count(anchor) == 1`, split, match inside) went red. All found by running the deletion mutant, never by reading.

## Code the suite cannot EXECUTE, pinned as TEXT — assert the effect, and weigh the cost of moving the code

- **Good looks like —** Regions no test can call (below a module's seam, inside `__main__`, a shell script body, top-level import-time control flow) get a **text** pin under the same bar as any declarative artifact (*Declarative artifacts* above owns the anchoring technique). It asserts the **effect the construct must produce**, never that the construct *exists*: *"a loop over the report is present"* is vocabulary, *"the loop's body reaches the log"* is the effect. Second half, the design cost: **relocating production code so a real unit test can reach it changes the thing that ships.** Pay it when the pin needs the code's **values** (an output over many inputs, an ordering, a format); don't when it needs only its **shape** — shape is a region-anchored source assertion at zero relocation risk.
- **Auditor checks —** `[D]` For each source-text pin, run the mutant that **keeps the named construct and removes its payload** (keep the loop, delete the call inside it; keep the branch, empty its body): does the suite go red? `[D]` **When the pin guards a FORBIDDEN construct — a spec's "fatal if ignored" trap — the mutant is not deletion, it is CONSTRUCTION: BUILD the forbidden implementation, in a different syntax from the one the spec named, and run it.** A pin phrased in the spec's own vocabulary (the wrapper's name, `.map(`) stays green against the same hazard written as an in-place `for` loop or inlined at one site. State what the pin forbids as the **hazard** (what must not be swallowed, reshaped, spawned), never as the construct that happens to cause it today. `[J]` Does the assertion name an effect — a value produced, a call reached, an order held — or a keyword a reader can satisfy without the behavior? `[D]` Is the assertion region-anchored (unique anchor asserted, then matched inside the slice) rather than whole-file? `[J]` Where the diff **moved** production code to make it testable, what does the pin actually need — values or shape? A move made for a shape-only pin is production surface bought for nothing. `[J]` Is the region's untestability recorded where the next author will meet it (the seam's own index/doc entry), or rediscovered every slice?
- **Incident —** 0041 S10a (2026-08-17), both halves in one slice. A pin asserted a `for…of` loop over a substitution report **exists**; the mutant that kept the loop and deleted the `log()` **inside** it survived — under a test whose own failure message names the defect it was written to prevent. Closed by asserting inside the matched loop body. The same slice relocated **three** helpers “so they can be pinned”; the reviewer's own later prescription covered an equivalent case with a **one-line** region-anchored assertion at zero relocation. One move earned itself (its output over many inputs was the defect); the other two bought ~two dozen lines of production surface each for defects a shape assertion already guards. *Recurred at S10b, inside the slice that inherited the rule: a pin guarding the spec's “fatal if ignored” trap asserted the guard's **vocabulary**, and the gate built **two** forbidden implementations green at HEAD. The class survives its own promotion; the constructed mutant, not the written rule, closes it.*

## Exemptions and allowlists inside a scan are themselves under test

- **Good looks like —** Every skip / exempt / allow branch is production logic. The branch set is **derived from the pattern or table itself**, never hand-listed in the test, so a branch added without fixtures goes red. Each branch is pinned **in both directions**: a fixture it legitimately admits, **and** a fixture where the same token rides a **live violation that must still be caught**. A guard named for one class admits **only** that class — a forward-looking or present-state clause inside a "past tense only" exemption disarms it silently, and reads as intentional forever after. Positive-only coverage proves the vocabulary is *live*; only the negative fixture proves the exemption is *narrow*.
- **Auditor checks —** `[D]` Is every branch of the exemption vocabulary exercised at all — parametrized over a set **derived** from the scan's own source? `[J]` For each branch, is there a fixture where that exact token appears in a real violation and the scan **still fires**? `[J]` Read each admitted phrase against the class the guard is named for: is it that class, or a different one that merely co-occurs with it? `[D]` Delete the exemption and re-run: which tests go red? (a guard nothing pins is decoration). `[J]` Is the exemption's measured **residual** written down — what it knowingly lets through — rather than implied to be zero?
- **Incident —** 0041 S6 (2026-08-14/15), the same defect **twice in one slice**, in the guard that had just become the **sole** mechanical custody of a class of stale shipped copy. Its contract was “history is not a denial”, and it was seeded with a **forward** clause naming the next slice — silently exempting a line that both promised that slice and made a false claim about today. Land fixed it red-first. The next round found a second member: a bare present-state negation (“is no longer *shipped*” is a live false claim, not history), narrowed to its honest collocations and pinned both ways.

## A scan's CORPUS is part of its contract — enumerate from the tracked tree, not the disk

- **Good looks like —** Any check that sweeps "every file of kind X" derives its list from the **version-controlled tree** (`git ls-files`, with a fail-loud `check=True` so a broken git raises rather than silently returning an empty corpus) — never a filesystem walk (`rglob` / `os.walk` / a recursive glob) rooted at the repo. **A working checkout is not the repo:** it also holds untracked material a walk swallows — vendored virtualenvs, tool caches, build output, and **linked worktrees parked inside the checkout**, each a full second copy of the files being swept. One enumeration convention per repo. The corpus is itself asserted with a **floor pin** (`len(candidates) >= N`) so an exclusion prefix that swallows the sweep fails loud instead of passing vacuously.
  **The same bar covers every OTHER input the scan DERIVES, above all its VOCABULARY** — the token set, pattern alternation or branch list parsed out of a source document. A derivation is lossy by construction: one row whose cell stops matching drops out silently, the scan runs over a narrower world, and every assertion stays green. Assert the derivation's **completeness**, not its non-emptiness — **where the source's cardinality is OWNED somewhere (a sibling guard, a schema, the document's own header), import that owner's count and assert EQUALITY**; a floor is the fallback only where cardinality is genuinely unbounded. Import the owner's *contract* rather than re-parsing the same document: two parsers over one table is what lets the two readings disagree, and a third parser written to prove they agree is the same defect again.
  **And the corpus of a repo-wide content scan includes the slice that ADDS it.** The plan record, the ledger line and the pin's own docstring are tracked files, graded from the moment the rule lands: write them to the rule and check them **before** committing. State the corpus's own limit in the same breath — a tracked-tree corpus sees the working tree and never git history, so a **commit message** is outside every such scan by construction (`docs-traceability.md` → *Change explainability* owns that half). *(0041 S11: the slice's own verdict record had to be authored token-free, and a commit message that had already landed carried three of the tokens and had to be amended — the amended-away copy stays in history, unscanned, permanently.)*
- **Auditor checks —** `[D]` Grep the scanners and their tests for `rglob(` / `os.walk(` / a recursive glob rooted at the repo root — each hit is a defect unless it is walking a directory it owns outright. `[D]` Run the sweep in **both** shapes — the maintainer's working checkout **and** a fresh clone or linked worktree — and diff the corpus **sizes**; they must match. `[J]` Does the scan reuse the repo's one enumeration helper, or hand-roll a second that will drift from it? `[D]` Is there a corpus floor assertion, so a too-aggressive exclusion cannot silently empty the sweep? `[J]` Is the chosen convention recorded **at the call site** (a do-not-revert comment), given no gate re-derives it? `[D]` For every set the scan DERIVES from a document, mutate the source so **one** member stops parsing (bold the cell, footnote it, re-case it) and re-run: does the suite go red, or does the set quietly shrink while the scan reports clean? `[D]` Is the derived set's size pinned against a cardinality some other file **owns**, or only against a floor / a non-empty check — which 1-of-N satisfies? `[J]` Does the scan's own docstring claim it delegates to that owner? A stated delegation is an assertion: make it mechanical or delete the claim.
- **Tradeoff —** A disk walk looks identical to the tracked listing on the machine it was written on. Because CI clones fresh, this defect **passes CI by construction** and surfaces only in the maintainer's checkout — the one place a release is cut from.
- **Incident —** 0041 S9 (2026-08-17). A pin enumerated markdown with `Path.rglob`. Measured in the maintainer's checkout: **129 `.md` files, 61 leaked from linked worktrees** under a gitignored `.claude/worktrees/`, against **60 files and zero leaks** via `git ls-files` — GREEN in a worktree, GREEN in CI, RED only where the land ran. Three scanners in the same repo already used `git ls-files`; the convention was real and written nowhere. With every worktree removed the walk still picked up 8 untracked `.md` from a vendored virtualenv and a tool cache. *Recurred at S11 (2026-08-18), the derived-VOCABULARY half, in a slice whose own spec CITED this dimension: a containment pin derived its forbidden-token set by regex from the document that DEFINES those tokens and asserted only non-emptiness. Bolding **one** cell dropped its token from the alternation, and republishing it elsewhere passed the **entire suite** — the sibling guard counted ROWS while the pin counted format-matching CELLS. Killed by importing the sibling's row-count contract and asserting equality.*

## Forward promises need a tripwire (a strict expected-failure that fires when the promise is KEPT)

- **Good looks like —** When code **registers something ahead of its writer** — a manifest entry, an annotation, a contract vouching for an artifact a later change will produce — the promise carries a **mechanical expiry**, not only a comment. Cheapest form: a **strict** expected-failure (`@pytest.mark.xfail(strict=True)`, `it.failing`) asserting the **fulfilled** state, so it is red today and red the moment the promise is kept, forcing whoever lands the later change to delete the marker and its comments. **Strictness is the whole point:** a lenient expected-failure passes in both worlds and guards nothing. *(Do-not-re-propose, 2026-08-14: pinning the strictness itself was considered and dropped — a meta-test reading its own source for the decorator argument guards against vandalism, not drift.)*
- **Auditor checks —** `[D]` Grep the diff for forward-looking registrations and comments (*will*, *once X lands*, *planned*, a TODO naming a future change) — for each, is there a test that **changes state** when the future arrives? `[D]` Is the marker **strict**? `[J]` Does the tripwire assert the *fulfilled* state (so it flips on success) rather than today's state (which flips on nothing)? `[J]` Is the abandonment branch written down — what the annotation becomes if the promised change is dropped?
- **Incident —** 0041 S4 (2026-08-13): a referential-closure gate accepted a new config path as an “init generates it” output while the init step that writes it was a **later slice of the same plan**. The registration's own instruction — *“if that slice is ever abandoned, re-annotate the class”* — had **no mechanism behind it**: drop the later slice and the gate vouches forever, green, for a file nothing produces. Three lines closed it, taken **together with** the wording fix that stopped asserting a plan-order convention as a *property* — the mechanical and verbal halves of one over-claim, neither working alone.

## Coverage of behavior, not vanity %

- **Auditor checks —** `[J]` Do tests assert outcomes a user/caller cares about, or do they over-specify private internals and mock call-order? `[J]` Any tests that execute code but assert nothing (or only `not throws`) where a real outcome should be checked? (see Test-diff review dimension for the diff-coverage gate) `[J]` Would these tests fail if the behavior silently changed — or only if the implementation is rewritten?

## Test-diff review (did the assertions/coverage get weaker?)

- **Auditor checks —** `[D]` Grep the diff for `skip`, `only`, `xit`, `xdescribe`, `@Disabled`, `@Ignore`, `pytest.mark.skip`, `todo`, commented-out assertions, widened tolerances. `[J]` For each removed/loosened assertion or regenerated snapshot: is there a stated, legitimate reason? `[D]` Diff-coverage tool shows changed lines didn't drop below threshold. `[J]` Did an expected value change *to follow* the implementation (rubber-stamping a regression) rather than reflecting an intended behavior change?

## Failure-path & edge-case coverage

- **Auditor checks —** `[J]` Are boundaries and invalid inputs tested, or only the typical case? `[J]` Is every error branch / `catch` / fallback exercised and its *effect* asserted (not just "didn't crash")? `[D]` Branch coverage on the changed unit (catches untested error arms). `[J]` Are failure modes of external dependencies simulated (inject timeout/5xx/exception) and the degradation asserted?

## Determinism (no flaky tests)

- **Auditor checks —** `[D]` Grep for nondeterminism smells: `sleep(`, `setTimeout`-then-assert, unseeded `random`, `Date.now()`/`new Date()`/`time.time()` in assertions, order-dependent fixtures, `@Retry`/`flaky`/`rerun` annotations masking instability. `[J]` Is async synchronized via await/poll on a condition rather than a magic delay? `[D]` Suite passes under randomized order (`--shuffle`/`-p randomly`) and on repeat runs. `[J]` Are known-flaky tests tracked and being fixed, not silently retried?

## Regression & snapshot tests

- **Auditor checks —** `[J]` Does each bug fix include a test that pins the corrected behavior and would have caught the original bug? `[D]` Snapshot files are committed and present in the diff. `[J]` Are snapshots scoped/meaningful (focused on what matters) rather than sprawling captures that get rubber-stamped on update? `[J]` Was a snapshot update in this diff *justified by an intended change*, not a silent regression auto-accepted?

## Visual-regression & accessibility testing (UI)

- **Good looks like —** UI changes are guarded by **visual-regression** diffs against an approved baseline across key viewports/themes (Playwright / Chromatic / Percy / Storybook), and by **automated a11y** checks (axe-core via Playwright/Cypress/Storybook, or `jest-axe`) that fail the build on WCAG violations. Automated a11y is a **floor, not a pass** — axe-core detects roughly half of issues (Deque 2021: ~57% across 13,000+ pages; older tool estimates ~30%) — backed by keyboard-nav and screen-reader passes per `product-ux.md`.
- **Auditor checks —** `[D]` axe/jest-axe assertions present on changed UI; build fails on new violations. `[D]` Visual baselines committed and diffs reviewed/approved (not auto-accepted). `[J]` Are critical states (loading/empty/error, focus, RTL, dark mode) captured, not just the happy render? `[J]` Is automated a11y treated as a floor with manual keyboard/SR coverage for what scanners miss?

## Contract testing (provider/consumer compatibility)

- **Auditor checks —** `[J]` Do changes to a published API/event have a contract test (pact, schema-compat, or stored-response verification) rather than relying on slow brittle end-to-end? `[D]` Provider verification / schema-back-compat check runs in CI and passes; broker "can-I-deploy" green where adopted. `[J]` Is the contract the genuine consumer expectation, kept in sync, not a stale hand-written stub? `[D]` Breaking-change detector (Buf/OpenAPI-diff) gates the published surface.
