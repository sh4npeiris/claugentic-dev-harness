# Testing — does the suite actually prove the behavior, and will it catch the next regression?

> **Loads when:** any change that adds, edits, or deletes tests; any behavior change that *should* be tested; refactors of legacy/untested code (characterization first); UI work (visual + a11y); flaky-test triage; or coverage/CI-gate changes.
> Method, tags, honesty register: `README.md` → *Reading a module*.
> **Governing rule across every dimension: trust the oracle, not the author's word.** "Tests pass" is necessary, never sufficient — the audit asks *what would have to break for this test to fail?*

---

## Test pyramid (shape of the suite: unit / integration / e2e)

- **Auditor checks —** `[J]` Is each new behavior tested at the cheapest level that proves it, or pushed up into a slow/broad test out of convenience? `[J]` Is there an inverted pyramid (many e2e, few unit) signalling untestable design? `[D]` Test-suite wall-clock time and per-tier counts (where the runner reports tiers/tags). `[J]` Do integration tests exercise the *real* seam (DB, serialization, HTTP contract) rather than mocking the very thing under test?

## Characterization tests & golden master (the equivalence oracle for legacy refactors)

- **Auditor checks —** `[J]` Does a non-trivial refactor of untested code introduce characterization/approval tests *before* the change (visible in commit order or PR narrative)? `[J]` Do they capture *actual* behavior, quirks and bugs included, rather than idealized behavior? `[D]` Golden-master baselines committed, diffable, regenerable by a documented command. `[J]` Are throwaway characterization tests later promoted to intent-revealing tests, or kept deliberately? `[J]` Has the baseline/oracle absorbed its adversarial pass **before** its first recorded run? The identical fix afterwards is indistinguishable from tuning the exam toward a wanted result, and the artifact then owes a defect-versus-tuning rule *(0044 S1a)*.

## Mutation testing (are the tests real?)

- **Auditor checks —** `[D]` Mutation run on the changed critical module; score meets the agreed threshold (e.g. ≥80% on core logic). `[J]` Are surviving mutants triaged (gap → add assertion; equivalent → justified suppression) rather than blanket-ignored? `[J]` Is the tool aimed at logic that matters, not vanity-run across trivial code? `[D]` Mutation config/CI step present where adopted. `[J]` For each **named central claim** in the diff (a test whose *name* asserts a structural property — "anchored to `__file__`, not the cwd" · "capped" · "byte-identical"), construct the exact wrong implementation the claim forbids and **run it**: does the suite go red? Four vacuity shapes recur (0041 S10a): the test **recomputes the implementation's own expression**; it asserts against the implementation's **own exported constant** (a tautology — the remedy is an **independent literal** in the test, so a swapped, dropped, reordered or added element is a diff); the **ambient environment makes right and wrong coincide** (the one cwd / locale / timezone / **working-tree shape** where both agree — run the mutant in the shape the defect *inhabits*); the pin **exercises a regime where the mechanism is inactive** (an overflow guard pinned only on inputs that never overflow); and the **corpus satisfies the assertion elsewhere**, so the mutant's target was never its only source (*Declarative artifacts* below owns the anchoring technique). `[J]` Is a boundary pinned from **both** sides (`n-1`, `n`, `n+1`) against a **fixed** reference, or from one side only — where `>` vs `>=` *and* a changed threshold both survive?
- **Incident —** 0041 S3 (2026-08-13), three load-bearing pins that asserted nothing. A `__file__`-vs-cwd pin recomputed its own expression and pytest runs from the root where both coincide → killed by a subprocess with `cwd=tmp_path` holding a **decoy** manifest. A 30-day boundary fed boundary **+5s** let `>`→`>=`, `30`→`7` and `abs()` all survive → killed by a `(29,F) (30,F) (31,T) (-31,F)` table against a **fixed** `now`. A "byte-identical" promise was pinned only where the reserve mechanism never bites. A genuinely **equivalent** mutant (`.isdecimal()`→`.isdigit()`, subsumed by a `try`) was proven so over all 1,114,112 code points and **left in place with the proof and the killable half named in the docstring** — the right disposition for an unkillable mutant.

## Declarative artifacts (CI workflows, manifests, config — and instruction files a human or agent executes) — assert the refusal, not the vocabulary

- **Good looks like —** Parse with a real parser; **scope** each assertion to the unit that owns the behavior (job · step · key); assert the **refusal or effect** (the `exit 1`, the `needs:` edge, the denied permission), never that a keyword appears somewhere. Cross-artifact parity is **derived** as a set relation plus an explicit floor, never hand-typed. **This dimension owns the anchoring technique** for an instruction artifact with no parser (a runbook, a prompt/skill file, a template an agent executes): assert the anchor occurs **exactly once**, split on it, assert **inside that slice** — never an ordinal index, never the whole file. Fixtures are **extracted from the artifact's own bytes**; a hand-transcribed copy tests your reading of the prose, not the prose.
- **Auditor checks —** `[D]` Delete the guard clause the test names and re-run: does the suite go red? (a whole-file substring assertion survives on a neighbouring `echo`, comment or error message). `[J]` Is each assertion anchored to its owning job/step/key, or searching the parsed document globally? `[J]` Does the test assert the artifact *refuses* the bad case, or only that it *mentions* the check? `[D]` Is the artifact parsed (YAML/JSON/TOML) rather than string-matched? `[J]` Is a parity list between two artifacts derived, or hand-maintained? `[D]` Count the asserted literal's occurrences **in the artifact itself**: more than one and a whole-file assertion is vacuous *by construction* — region-scope it, then re-run the deletion mutant. `[D]` Is every fixture for an instruction artifact derived from that artifact, or hand-transcribed?
- **Incident —** Three, same repo. (1) `/build` and `/condense` shipped across v0.4.0–v0.5.1 with **unparseable YAML frontmatter** — three releases loading with empty metadata, because nothing parsed them. (2) 0041 S2 (2026-08-12): a hand sweep of **13 mutants left 9 alive** — deleting a lease comparison *and its `exit 1`*, and deleting the tag↔manifest refusal, each left the suite 26/26 green because a surviving `echo` carried every asserted string; fixed by a `_step_run(job, name_fragment)` helper failing loud on 0-or-2 matches, and a hand-typed parity list became `gate_scripts(ci) ⊆ gate_scripts(release)` plus a floor. (3) 0041 S7 (2026-08-16), the same defect **twice in one slice, the second inside the fix for the first**: a whole-file substring pinned a path occurring eight times, so deleting the slice's headline row left all 638 tests green; the region-scoped fix (`text.count(anchor) == 1`, split, match inside) went red. All found by running the mutant, never by reading.

## Code the suite cannot EXECUTE, pinned as TEXT — assert the effect, and weigh the cost of moving the code

- **Good looks like —** Regions no test can call (below a module's seam, inside `__main__`, a shell body, import-time control flow) get a **text** pin under the same bar as any declarative artifact (*Declarative artifacts* above owns the anchoring technique), asserting the **effect the construct must produce**, never that it *exists*: *"a loop over the report is present"* is vocabulary, *"the loop's body reaches the log"* is the effect. Second half, the design cost: **relocating production code so a real unit test can reach it changes the thing that ships** — pay it for **values** (an output over many inputs, an ordering, a format), never for **shape**.
- **Auditor checks —** `[D]` For each source-text pin, run the mutant that **keeps the named construct and removes its payload** (keep the loop, delete the call inside it): does the suite go red? `[D]` **When the pin guards a FORBIDDEN construct — a spec's "fatal if ignored" trap — the mutant is not deletion but CONSTRUCTION: BUILD the forbidden implementation, in a different syntax from the one the spec named, and run it.** A pin phrased in the spec's vocabulary (the wrapper's name, `.map(`) stays green against the same hazard written as an in-place `for` loop. State what the pin forbids as the **hazard** (what must not be swallowed, reshaped, spawned), never as today's construct. `[J]` Does the assertion name an effect — a value produced, a call reached, an order held — or a keyword satisfiable without the behavior? `[D]` Is it region-anchored rather than whole-file? `[J]` Where the diff **moved** production code to make it testable, does the pin need values or shape? A move for a shape-only pin is production surface bought for nothing. `[J]` Is the region's untestability recorded where the next author meets it (the seam's own index/doc entry)?
- **Incident —** 0041 S10a (2026-08-17), both halves in one slice. A pin asserted a `for…of` loop over a substitution report **exists**; the mutant keeping the loop and deleting the `log()` inside it survived — under a test whose own failure message names the defect it was written to prevent. The same slice relocated **three** helpers "so they can be pinned": one earned itself, the other two bought ~two dozen lines of production surface each for defects a **one-line** region-anchored assertion already guards. *Recurred at S10b, inside the slice that inherited the rule: a pin on a "fatal if ignored" trap asserted the guard's **vocabulary**, and the gate built **two** forbidden implementations green at HEAD. The constructed mutant, not the written rule, closes the class.*

## Exemptions and allowlists inside a scan are themselves under test

- **Good looks like —** Every skip / exempt / allow branch is production logic: positive-only coverage proves the vocabulary is *live*, only the negative fixture proves the exemption is *narrow*.
- **Auditor checks —** `[D]` Is every branch of the exemption vocabulary exercised — parametrized over a set **derived** from the scan's own source? `[J]` For each branch, is there a fixture where that exact token appears in a real violation and the scan **still fires**? `[J]` Read each admitted phrase against the class the guard is named for: is it that class, or one that merely co-occurs with it? `[D]` Delete the exemption and re-run: which tests go red? (a guard nothing pins is decoration). `[J]` Is the exemption's measured **residual** written down — what it knowingly lets through — rather than implied to be zero?
- **Incident —** 0041 S6 (2026-08-14/15), the same defect **twice in one slice**, in the guard that had just become the **sole** mechanical custody of a class of stale shipped copy. Its contract was "history is not a denial", and it shipped with a **forward** clause naming the next slice — silently exempting a line that both promised that slice and made a false claim about today. The next round found a second member: a bare present-state negation ("is no longer *shipped*" is a live false claim, not history), narrowed to its honest collocations and pinned both ways.

## A scan's CORPUS is part of its contract — enumerate from the tracked tree, not the disk

- **Good looks like —** `git ls-files` with a fail-loud `check=True`, one enumeration convention per repo, plus a **floor pin** (`len(candidates) >= N`). **A working checkout is not the repo:** a walk also swallows vendored virtualenvs, tool caches, build output and **linked worktrees parked inside the checkout**, each a full second copy. **The same bar covers every OTHER input the scan DERIVES, above all its VOCABULARY** — a derivation is lossy by construction, so assert **completeness**, not non-emptiness, and import the owner's *contract* rather than re-parsing the document a second time. **The corpus of a repo-wide content scan includes the slice that ADDS it** — plan record, ledger line and the pin's own docstring are tracked files, graded from the moment the rule lands — and it sees the working tree, never git history, so a **commit message** is outside every such scan by construction (`docs-traceability.md` → *Change explainability* owns that half). *(0041 S11: an already-landed commit message carried three forbidden tokens and had to be amended — the amended-away copy stays in history, unscanned, permanently.)*
- **Auditor checks —** `[D]` Grep the scanners and their tests for `rglob(` / `os.walk(` / a recursive glob rooted at the repo root — each hit is a defect unless it walks a directory it owns outright. `[D]` Run the sweep in **both** shapes — the maintainer's checkout **and** a fresh clone or linked worktree — and diff the corpus **sizes**; they must match. `[J]` Does the scan reuse the repo's one enumeration helper, or hand-roll a second? `[D]` Is there a corpus floor assertion? `[J]` Is the convention recorded **at the call site** (a do-not-revert comment), given no gate re-derives it? `[D]` For every set the scan DERIVES from a document, mutate the source so **one** member stops parsing (bold the cell, footnote it, re-case it): does the suite go red, or does the set quietly shrink while the scan reports clean? `[D]` Is the derived set's size pinned against a cardinality another file **owns**, or only against a floor / non-empty check — which 1-of-N satisfies? `[J]` Does the scan's docstring claim it delegates to that owner? A stated delegation is an assertion: make it mechanical or delete the claim.
- **Incident —** 0041 S9 (2026-08-17). A pin enumerated markdown with `Path.rglob`. Measured in the maintainer's checkout: **129 `.md` files, 61 leaked from linked worktrees** under a gitignored `.claude/worktrees/`, against **60 files and zero leaks** via `git ls-files` — GREEN in a worktree, GREEN in CI (which clones fresh, so this class passes CI *by construction*), RED only where the land ran. Three scanners in the repo already used `git ls-files`; the convention was real and written nowhere. With every worktree removed the walk still picked up 8 untracked `.md` from a vendored virtualenv and a tool cache. *Recurred at S11 (2026-08-18), the derived-VOCABULARY half, in a slice whose spec CITED this dimension: a containment pin derived its forbidden-token set by regex from the document DEFINING those tokens and asserted only non-emptiness. Bolding **one** cell dropped its token, and republishing it elsewhere passed the **entire suite** — the sibling guard counted ROWS, the pin counted format-matching CELLS. Killed by importing the sibling's row-count contract and asserting equality.*

## A checker's VERDICT is part of its contract — what it measured decides, and a narrowed run says so

- **Good looks like —** A tool that emits a pass/fail owes two totalities. **Measurement:** every quantity the run collects either **enters the verdict** or is printed as *advisory* — a figure in the report while the exit code is computed from a narrower set is a green light with the evidence for red already on screen. **Scope:** a run narrowed by a flag (`--only`, `-k`, a subset filter) prints **what it covered** and can never reach the unqualified verdict line.
- **Auditor checks —** `[D]` For each figure the tool prints, break the thing it measures and re-run: does the **exit code** move, or only the report? `[J]` Is any collected quantity neither in the verdict nor labelled advisory? `[D]` Run each narrowing flag: does the verdict line name the subset, and is the unqualified line unreachable from it? `[J]` Is a narrowed run's transcript distinguishable from a full run's?
- **Incident —** 0044 S1a (2026-08-20), **three in one slice**, in an instrument whose whole job is emitting verdicts. A hazard probe collected a dead endpoint's connection attempts and their gaps, printed them, and scored on *"still running at the bound"* alone — a 24-attempt no-backoff retry storm scored AVOIDED. The calibration runner printed `12/13` held-out in its own table and **exited 0**: neither held-out nor spec-compliance drift reached `problems`. And `--only <id>` printed the unqualified pass line off **1 of 13** cases with the completeness check suppressed — indistinguishable from a real run in a transcript. All three were found by reading the report against the exit code, never by the suite.

## Forward promises need a tripwire (a strict expected-failure that fires when the promise is KEPT)

- **Good looks like —** When code **registers something ahead of its writer** — a manifest entry, an annotation, a contract vouching for an artifact a later change will produce — the promise carries a **mechanical expiry**, not only a comment. Cheapest form: a **strict** expected-failure (`@pytest.mark.xfail(strict=True)`, `it.failing`) asserting the **fulfilled** state, so it is red today and red the moment the promise is kept, forcing whoever lands the later change to delete the marker. **Strictness is the whole point:** a lenient expected-failure passes in both worlds and guards nothing. *(Do-not-re-propose, 2026-08-14: pinning the strictness itself — a meta-test reading its own source for the decorator argument — guards against vandalism, not drift.)*
- **Auditor checks —** `[D]` Grep the diff for forward-looking registrations and comments (*will*, *once X lands*, *planned*, a TODO naming a future change) — for each, is there a test that **changes state** when the future arrives? `[D]` Is the marker **strict**? `[J]` Does the tripwire assert the *fulfilled* state (so it flips on success) rather than today's state (which flips on nothing)? `[J]` Is the abandonment branch written down — what the annotation becomes if the promised change is dropped?
- **Incident —** 0041 S4 (2026-08-13): a referential-closure gate accepted a new config path as an "init generates it" output while the init step writing it was a **later slice of the same plan**. The registration's own instruction — *"if that slice is ever abandoned, re-annotate the class"* — had **no mechanism behind it**: drop the later slice and the gate vouches forever, green, for a file nothing produces. Three lines closed it, **together with** the wording fix that stopped asserting a plan-order convention as a *property* — the mechanical and verbal halves of one over-claim, neither working alone.

## Coverage of behavior, not vanity %

- **Auditor checks —** `[J]` Do tests assert outcomes a user/caller cares about, or over-specify private internals and mock call-order? `[J]` Any tests that execute code but assert nothing (or only `not throws`) where a real outcome should be checked? (the diff-coverage gate lives in *Test-diff review*) `[J]` Would these tests fail if the behavior silently changed — or only if the implementation is rewritten?

## Test-diff review (did the assertions/coverage get weaker?)

- **Auditor checks —** `[D]` Grep the diff for `skip`, `only`, `xit`, `xdescribe`, `@Disabled`, `@Ignore`, `pytest.mark.skip`, `todo`, commented-out assertions, widened tolerances. `[J]` For each removed/loosened assertion or regenerated snapshot: is there a stated, legitimate reason? `[D]` Diff-coverage tool shows changed lines didn't drop below threshold. `[J]` Did an expected value change *to follow* the implementation (rubber-stamping a regression) rather than reflecting an intended behavior change?

## Failure-path & edge-case coverage

- **Auditor checks —** `[J]` Are boundaries and invalid inputs tested, or only the typical case? `[J]` Is every error branch / `catch` / fallback exercised and its *effect* asserted (not just "didn't crash")? `[D]` Branch coverage on the changed unit (catches untested error arms). `[J]` Are failure modes of external dependencies simulated (inject timeout/5xx/exception) and the degradation asserted?

## Determinism (no flaky tests)

- **Auditor checks —** `[D]` Grep for nondeterminism smells: `sleep(`, `setTimeout`-then-assert, unseeded `random`, `Date.now()`/`new Date()`/`time.time()` in assertions, order-dependent fixtures, `@Retry`/`flaky`/`rerun` annotations masking instability. `[J]` Is async synchronized via await/poll on a condition rather than a magic delay? `[D]` Suite passes under randomized order (`--shuffle`/`-p randomly`) and on repeat runs. `[J]` Are known-flaky tests tracked and being fixed, not silently retried?

## Regression & snapshot tests

- **Auditor checks —** `[J]` Does each bug fix include a test that pins the corrected behavior and would have caught the original bug? `[D]` Snapshot files committed and present in the diff. `[J]` Are snapshots scoped/meaningful rather than sprawling captures that get rubber-stamped on update? `[J]` Was a snapshot update *justified by an intended change*, not a silent regression auto-accepted?

## Visual-regression & accessibility testing (UI)

- **Good looks like —** UI changes are guarded by **visual-regression** diffs against an approved baseline across key viewports/themes (Playwright / Chromatic / Percy / Storybook), and by **automated a11y** checks (axe-core via Playwright/Cypress/Storybook, or `jest-axe`) failing the build on WCAG violations. Automated a11y is a **floor, not a pass** — axe-core detects roughly half of issues (Deque 2021: ~57% across 13,000+ pages; older tool estimates ~30%) — backed by keyboard-nav and screen-reader passes per `product-ux.md`.
- **Auditor checks —** `[D]` axe/jest-axe assertions present on changed UI; build fails on new violations. `[D]` Visual baselines committed and diffs reviewed/approved (not auto-accepted). `[J]` Are critical states (loading/empty/error, focus, RTL, dark mode) captured, not just the happy render? `[J]` Is automated a11y treated as a floor with manual keyboard/SR coverage for what scanners miss?

## Contract testing (provider/consumer compatibility)

- **Auditor checks —** `[J]` Do changes to a published API/event have a contract test (pact, schema-compat, or stored-response verification) rather than slow brittle end-to-end? `[D]` Provider verification / schema-back-compat check runs in CI and passes; broker "can-I-deploy" green where adopted. `[J]` Is the contract the genuine consumer expectation, kept in sync, not a stale hand-written stub? `[D]` Breaking-change detector (Buf/OpenAPI-diff) gates the published surface.
