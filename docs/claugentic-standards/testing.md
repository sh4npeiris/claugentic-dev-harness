# Testing — does the suite actually prove the behavior, and will it catch the next regression?

> **Loads when:** any change that adds, edits, or deletes tests; any behavior change that *should* be tested; refactors of legacy/untested code (characterization first); UI work (visual + a11y); flaky-test triage; or coverage/CI-gate changes.
> **ISO/IEC 25010:** Maintainability (testability, analysability, modifiability), with Reliability and Functional-suitability — cross-cutting; tests are the safety net every other dimension leans on. · **Status:** draft

Each entry below is one **auditable dimension**. Per change, the reviewer applies the
*relevant* ones **fully** (select-don't-skip), right-sized to the change — never
gold-plating an irrelevant one, never skipping a relevant one.

The governing rule across every dimension: **trust the oracle, not the author's word.** A test is only worth its green check if a real defect would have turned it red. "Tests pass" is necessary, never sufficient — the audit asks *what would have to break for this test to fail?*

## Test pyramid (shape of the suite: unit / integration / e2e)

- **Good looks like —** Most tests are fast, isolated **unit** tests (the wide base); fewer **integration** tests prove components wired together (real DB/queue/HTTP via testcontainers or in-memory doubles at trust boundaries); a thin top of **end-to-end** tests covers only critical user journeys. The new code's tests sit at the **lowest level that can still prove the behavior** — logic is unit-tested, not exercised only through a slow browser test. No "ice-cream cone" (e2e-heavy) or untested middle.
- **Auditor checks —** `[J]` Is each new behavior tested at the cheapest level that proves it, or pushed up into a slow/broad test out of convenience? `[J]` Is there an inverted pyramid (many e2e, few unit) signalling untestable design? `[D]` Test-suite wall-clock time and per-tier counts (where the runner reports tiers/tags). `[J]` Do integration tests exercise the *real* seam (DB, serialization, HTTP contract) rather than mocking the very thing under test?
- **Confidence —** `mixed`
- **Tradeoff (plain English) —** Lots of small fast tests find bugs in seconds and rarely break for the wrong reason; a few big slow tests are realistic but flaky and expensive. Get the mix wrong (all big tests) and the suite becomes so slow and unreliable the team stops trusting it.
- **Sources —** Test Pyramid — Mike Cohn, *Succeeding with Agile* (2009); Martin Fowler, "The Practical Test Pyramid" & bliki "TestPyramid"; *Software Engineering at Google* ch. 11 (test sizes: small/medium/large).

## Characterization tests & golden master (the equivalence oracle for legacy refactors)

- **Good looks like —** Before refactoring code that lacks tests, a **characterization test** pins the code's *current* observable behavior — not what it *should* do, what it *does* — so the refactor can be proven behavior-preserving. For wide/opaque output (a report, a render, a serialized blob), a **golden-master / approval** snapshot captures a representative input→output corpus as the reviewable baseline; the refactor passes iff outputs are byte-identical (or diffs are explicitly approved). Characterization tests are written *first*, then the change.
- **Auditor checks —** `[J]` Does a non-trivial refactor of previously-untested code introduce characterization/approval tests *before* the change (visible in commit order or PR narrative)? `[J]` Do they capture *actual* behavior (including known-quirky/buggy output) rather than asserting idealized behavior? `[D]` Golden-master baseline files are committed, diffable, and regenerable by a documented command. `[J]` Once the code is understood, are throwaway characterization tests promoted to intent-revealing tests or kept deliberately?
- **Confidence —** `mixed`
- **Tradeoff (plain English) —** They let you safely change scary code you don't fully understand by locking in "whatever it does today" as the contract. The cost: they bless current bugs as expected (must be revisited later), and a too-thin corpus gives false safety. Skipping them on a legacy refactor means flying blind — silent behavior changes ship.
- **Sources —** Michael Feathers, *Working Effectively with Legacy Code* (2004) — coined "characterization test"; Golden Master / Approval Testing (ApprovalTests, `llewellyn falco`); understandlegacycode.com (characterization vs approval vs regression).

## Mutation testing (are the tests real?)

- **Good looks like —** For critical or complex logic, test strength is validated by **mutation testing**: a tool (Stryker for JS/TS, PIT for Java, `mutmut`/`cosmic-ray` for Python, etc.) injects small faults ("mutants" — flip `>` to `>=`, `&&` to `||`, delete a statement) and the suite must **kill** them (a test turns red). **Surviving mutants** flag assertions that are missing, too weak, or code paths exercised-but-not-verified. A mutation-score threshold guards critical modules; equivalent mutants are reviewed/suppressed, not ignored wholesale.
- **Auditor checks —** `[D]` Mutation run on the changed critical module; score meets the agreed threshold (e.g. ≥80% on core logic). `[J]` Are surviving mutants triaged (genuine gap → add assertion; equivalent → justified suppression) rather than blanket-ignored? `[J]` Is the tool aimed at logic that matters, not vanity-run across trivial code? `[D]` Mutation config/CI step present where the team has adopted it. `[J]` For each **named central claim** in the diff (a test whose *name* asserts a structural property — "anchored to `__file__`, not the cwd" · "capped" · "byte-identical"), construct the exact wrong implementation the claim forbids and **run it**: does the suite go red? Four vacuity shapes recur — the test **recomputes the implementation's own expression** on both sides, or compares the implementation's output to the implementation's **own exported constant** (a tautology; the remedy is an **independent literal** written out in the test, so a swapped, dropped, reordered or added element is a diff — 0041 S10a: a default review-panel set was "pinned" only against itself, and all four of those mutants survived); the **ambient environment makes right and wrong coincide** (the suite runs from the one cwd / locale / timezone / **working-tree shape** where both agree — run the mutant in the shape the defect *inhabits*, not the shape you happen to be standing in); and the pin **exercises a regime where the mechanism is inactive** (an overflow guard pinned only on inputs that never overflow); and the **corpus already satisfies the assertion elsewhere** — the artifact under test contains the asserted string twice, so the mutant's target was never the only source (see *Declarative artifacts* below for the anchoring technique). `[J]` Is a boundary pinned from **both** sides (`n-1`, `n`, `n+1`) against a **fixed** reference, or from one side only — where `>` vs `>=` *and* a changed threshold both survive?
- **Confidence —** `mixed`
- **Tradeoff (plain English) —** It's the only test that tests your tests — it proves a real bug would be caught, which coverage % cannot. The cost is runtime (it re-runs the suite once per mutant, so it's slow) and noise from "equivalent" mutants that can't be killed. Skipping it means high coverage can still hide assertion-free tests that never actually check anything.
- **Incident that motivated this (delete this rule once its cause is gone) —** Plan 0041 Slice 3 (2026-08-13): three of the slice's own load-bearing pins asserted nothing. (1) The test named `..._anchored_to_the_plugin_not_the_cwd` **recomputed the same `__file__` expression** it was checking, and pytest runs from the repo root where a `__file__` anchor and a cwd anchor coincide — so replacing the constant with the exact forbidden `Path(".claude-plugin/plugin.json").resolve()` left **79/79 green**. Fixed by spawning the module in a subprocess with `cwd=tmp_path` holding a **decoy** manifest: the wrong implementation now reads the decoy and the pin goes red. (2) The 30-day-boundary test fed boundary **+5s** — younger than the boundary — so `>`→`>=`, `30`→`7` and `abs()` all survived; a four-row table `(29,F) (30,F) (31,T) (-31,F)` against a **fixed** `now` killed all three and removed the suite's last wall-clock read. (3) A "the agent-facing string is byte-identical" promise was pinned only on short fixtures **where the reserve mechanism never bites**, so a mutant leaking the reserved budget into that string survived all 93 tests; one assertion inside the existing overflow case closed it. In the same review a genuinely **equivalent** mutant (`.isdecimal()`→`.isdigit()`, subsumed by a `try`) was proven equivalent by an exhaustive sweep of all 1,114,112 code points, then **left in place with the equivalence proof and the name of the killable half recorded in the code's own docstring** — the right disposition for a mutant that cannot be killed.
- **Sources —** Mutation-testing literature — `R. DeMillo` et al. (1978) "Hints on Test Data Selection"; `Y. Jia` & `M. Harman`, "An Analysis and Survey of the Development of Mutation Testing" (IEEE TSE 2011); Stryker Mutator docs; PIT (pitest.org); *Software Engineering at Google* (coverage vs effectiveness).

## Declarative artifacts (CI workflows, manifests, config — and instruction files a human or agent executes) — assert the refusal, not the vocabulary

- **Good looks like —** A test over a declarative artifact (a CI workflow, a plugin/package manifest, a schema or policy file) **parses** it with a real parser rather than regexing text; **scopes** each assertion to the unit that owns the behavior — the job, the step, the key — not the whole file; and asserts the **refusal or effect** the artifact must produce (the `exit 1`, the `needs:` edge, the denied permission), never that a keyword merely *appears somewhere*. A cross-artifact parity rule ("workflow B runs every gate workflow A runs") is **derived** from both artifacts as a set relation plus an explicit floor — never a hand-typed list that goes stale silently. The same bar covers an **instruction artifact with no parser** — a runbook, a prompt/skill file, a template an agent executes. There the scoping technique is a **uniqueness-asserted region anchor**: assert the anchor occurs **exactly once**, split on it, assert **inside that slice** — never an ordinal index, never the whole file. And any **fixture or e2e scaffold is extracted from the artifact's own bytes**, never hand-typed: a hand-transcribed copy tests your reading of the prose, not the prose.
- **Auditor checks —** `[D]` Delete the guard clause the test names and re-run: does the suite go red? (a whole-file substring assertion survives, because a neighbouring `echo`, comment or error message still carries the string). `[J]` Is each assertion anchored to its owning job/step/key, or does it search the parsed document globally? `[J]` Does the test assert the artifact *refuses* the bad case, or only that it *mentions* the check? `[D]` Is the artifact parsed (YAML/JSON/TOML) rather than string-matched, so a shape break fails loud in the suite rather than silently at runtime? `[J]` Is a parity list between two artifacts derived, or hand-maintained? `[D]` Count the asserted literal's occurrences **in the artifact itself**: more than one and a whole-file assertion is vacuous *by construction* — region-scope it, then re-run the deletion mutant. `[D]` Is every fixture for an instruction artifact derived from that artifact (extracted/parsed), or hand-transcribed?
- **Confidence —** `mixed`
- **Tradeoff (plain English) —** Config files are code with no compiler and no runtime coverage — a broken workflow or manifest fails in production, once, at the worst moment. Testing them is cheap; testing them *badly* is worse than not testing, because a green "the workflow checks X" invites everyone to stop reading the workflow. The cost is a few lines of parse-and-scope plumbing per assertion.
- **Incident that motivated this (delete this rule once its cause is gone) —** Two, four weeks apart, same repo. (1) `/build` and `/condense` shipped across v0.4.0–v0.5.1 with **unparseable YAML frontmatter** — the skills loaded with empty metadata for three releases because nothing parsed them. (2) Plan 0041 Slice 2 (2026-08-12): a hand sweep of **13 mutants against the new release-workflow tests left 9 alive** — deleting the concurrent-publish lease comparison *and its `exit 1`*, and deleting the tag↔manifest version refusal, each left the suite 26/26 green because a surviving `echo` in an adjacent step still contained every asserted string. Fix: a `_step_run(job, name_fragment)` helper that fails loud on 0-or-2 matches, plus assertions naming the literal construct **and** its `exit 1`. In the same review, a hand-typed gate-parity list was replaced by `gate_scripts(ci.gates) ⊆ gate_scripts(release.gates)` with the four current gates as an explicit floor. (3) Plan 0041 Slice 7 (2026-08-16), the same defect **twice in one slice** — the second time **inside the fix for the first**. The slice's headline capability (one managed-set table row in a prose skill that copies a gate into the adopter's repo) was pinned by a whole-file substring; the asserted path occurred eight times in that file by then, so **deleting the row left the whole 638-test suite green** — the prose *discussing* the gate satisfied the pin the test's own comment said it could not. The region-scoped fix (`text.count(anchor) == 1`, split, match inside) went red under that mutant. Then the new pin written for the *prose remediation* searched the whole skill — which also contains the template the prose quotes — so deleting the quoted chain line stayed green, and drifting it to a different flag stayed green: it guarded the one string in the slice whose drift is destructive (the line an adopter is told to paste into a commit hook). Both were found only by running the deletion mutant, never by reading.
- **Sources —** cross-ref *Mutation testing* above (this dimension is that one applied to non-executable artifacts); *Software Engineering at Google* ch. 11 (assert what a caller observes); Fowler, "TestCoverage" (a green check is worth only what a real defect would turn red).

## Code the suite cannot EXECUTE, pinned as TEXT — assert the effect, and weigh the cost of moving the code

- **Good looks like —** Every codebase has regions no test can call: below a module's testable seam, inside a `__main__` block, a shell script's body, a top-level control flow that runs on import. A pin over such a region is a **text** assertion and carries the same bar as any declarative artifact (*Declarative artifacts* above owns the technique — assert the anchor is unique, split on it, match **inside** that slice): it asserts the **effect the construct must produce**, never that the construct *exists*. *"A loop over the report is present"* is vocabulary; *"the loop's body reaches the log"* is the effect — and the mutant that separates them is the one that keeps the construct and deletes its payload. Second half, the design cost: **relocating production code so a real unit test can reach it is a change to the thing that ships.** Pay it when the pin needs the code's **values** (an output over many inputs, an ordering, a format); don't pay it when the pin needs only its **shape** (this branch reads the parsed value; that loop logs) — shape is a region-anchored source assertion at zero relocation risk.
- **Auditor checks —** `[D]` For each source-text pin, run the mutant that **keeps the named construct and removes its payload** (keep the loop, delete the call inside it; keep the branch, empty its body): does the suite go red? `[D]` **When the pin guards a FORBIDDEN construct — a spec's "fatal if ignored" trap — the mutant is not deletion, it is CONSTRUCTION: BUILD the forbidden implementation, in a different syntax from the one the spec named, and run it.** A pin phrased in the spec's own vocabulary (the wrapper's name, `.map(`) stays green against the same hazard written as an in-place `for` loop or inlined at one site. State what the pin forbids as the **hazard** (what must not be swallowed, reshaped, spawned), never as the construct that happens to cause it today. `[J]` Does the assertion name an effect — a value produced, a call reached, an order held — or a keyword a reader can satisfy without the behavior? `[D]` Is the assertion region-anchored (unique anchor asserted, then matched inside the slice) rather than whole-file? `[J]` Where the diff **moved** production code to make it testable, what does the pin actually need — values or shape? A move made for a shape-only pin is production surface bought for nothing. `[J]` Is the region's untestability recorded where the next author will meet it (the seam's own index/doc entry), or rediscovered every slice?
- **Confidence —** `mixed` — the keep-the-construct/remove-the-payload mutant is a measurement; values-vs-shape is a reviewer's call.
- **Tradeoff (plain English) —** A test that only checks a line still exists reads as coverage and proves nothing — and it is worse than no test, because its own name convinces the next reader the behavior is guarded. Asserting the effect costs one more line. The other half is restraint: shuffling working code around purely to make testing easier is a real change to what ships, and it should buy something.
- **Incident that motivated this (delete this rule once its cause is gone) —** Plan 0041 Slice 10a (2026-08-17), both halves in one slice. The pin for the *"a substituted default is never silent"* fix asserted that a `for…of` loop over the substitution report **exists** in the control flow; a mutant that kept the loop and deleted the `log()` **inside** it survived — under a test whose own failure message names the defect it was written to prevent. Its sibling one seam over was deletable-green for the same reason. Both closed by asserting inside the matched loop body. In the same slice **three** helpers were relocated into the testable region "so they can be pinned" — and the reviewer's own later prescription then covered an equivalent below-the-seam case with a **one-line** region-anchored source assertion at zero relocation. One of the three moves earned itself: the moved code built an agent prompt whose *output over many inputs* was the defect (a narrowing clause emitted before the role framing and glued to it with no separator — it had survived two prior patches to that same line). The other two bought roughly two dozen lines of production surface each for defects a shape assertion already guards. *Recurred one slice later — 0041 S10b (2026-08-17), inside the slice that inherited this rule from 10a's harvest: the pin guarding the spec's own "fatal if ignored" trap 1 asserted the guard's vocabulary, and the gate built **two** implementations of the forbidden behaviour (a blanket guard written as an in-place `for` loop; the honesty thunk swallowing on its own) that were **green at HEAD** and were killed only by the corrected effect pin. The implementer had caught one sibling of this class in its own round and missed this one — the class survives its own promotion, and it is the constructed mutant, not the written rule, that closes it.*
- **Sources —** cross-ref *Declarative artifacts* above (same bar; it owns the anchoring technique) and *Mutation testing* above (the keep-the-construct mutant is that discipline applied to a text pin); M. Feathers, *Working Effectively with Legacy Code* (2004) — seams, and the cost of cutting one; D.H. Hansson, "Test-induced design damage" (2014) for the restraint half.

## Exemptions and allowlists inside a scan are themselves under test

- **Good looks like —** Every skip / exempt / allow branch inside a scan, linter, guard or policy check is treated as production logic. The branch set is **derived from the pattern or table itself**, never hand-listed in the test, so a branch added without fixtures goes red. Each branch is pinned **in both directions**: a fixture the branch legitimately admits, **and** a fixture where the same token rides a **live violation that must still be caught**. A guard named for one class admits **only** that class — a forward-looking or present-state clause sitting inside a "past tense only" exemption disarms it silently, and reads as intentional forever after. Positive-only coverage proves the vocabulary is *live*; only the negative fixture proves the exemption is *narrow*.
- **Auditor checks —** `[D]` Is every branch of the exemption vocabulary exercised at all — parametrized over a set **derived** from the scan's own source? `[J]` For each branch, is there a fixture where that exact token appears in a real violation and the scan **still fires**? `[J]` Read each admitted phrase against the class the guard is named for: is it that class, or a different one that merely co-occurs with it? `[D]` Delete the exemption and re-run: which tests go red? (a guard nothing pins is decoration). `[J]` Is the exemption's measured **residual** written down — what it knowingly lets through — rather than implied to be zero?
- **Confidence —** `mixed` — branch coverage is mechanical; whether a phrase belongs to the admitted class is a reviewer call.
- **Tradeoff (plain English) —** An exemption is the one part of a check that can only ever make it quieter, so a mistake there is invisible by construction: the suite stays green and the scan stops seeing things. One extra fixture per admitted phrase is the whole cost, and writing the "must still be caught" fixture is what exposes a bad phrase — the author discovers it while typing the test, not two rounds later.
- **Incident that motivated this (delete this rule once its cause is gone) —** Plan 0041 Slice 6 (2026-08-14/15), the same defect **twice in one slice**, in the guard that had just become the **sole** mechanical custody of a class of stale shipped copy. The guard's contract was "history is not a denial", and it was seeded with a **forward** clause naming the next slice — measured, a line that both promised that slice and made a false claim about today was silently exempted. Land fixed it with a red-first test. The very next review round found a second member: a bare present-state negation ("is no longer *shipped*" is a live false claim, not history), narrowed to its honest collocations and pinned both ways. The same round found the *scanner's* markers had no positive coverage at all and added it — leaving the **exemption** vocabulary as the one set still without both-directions coverage.
- **Sources —** cross-ref *Mutation testing* and *Declarative artifacts* above (this is those two applied to the quiet half of a check); Google Testing Blog, "Testing on the Toilet: Change-Detector Tests Considered Harmful" (a check that can be silenced without a red test is not a check).

## A scan's CORPUS is part of its contract — enumerate from the tracked tree, not the disk

- **Good looks like —** Any check that sweeps "every file of kind X" derives its file list from the **version-controlled tree** (`git ls-files`, with a fail-loud `check=True` so a broken git raises rather than silently returning an empty corpus) — never from a filesystem walk (`rglob` / `os.walk` / a recursive glob) rooted at the repo. **A working checkout is not the repo:** it also holds untracked material a walk silently swallows — vendored virtualenvs, tool caches, build output, and **linked worktrees parked inside the checkout**, each a full second copy of the very files being swept. One enumeration convention per repo, used by every scanner and every pin. The corpus is itself asserted: a **floor pin** (`len(candidates) >= N`) so an exclusion prefix that swallows the sweep fails loud instead of passing vacuously. **The same bar covers every OTHER input the scan DERIVES, above all its VOCABULARY** — the token set, pattern alternation or branch list it parses out of a source document. A derivation is lossy by construction: one row whose cell stops matching the parser drops out of the set silently, the scan keeps running over a narrower world, and every assertion in the file stays green. So assert the derivation's **completeness**, not merely its non-emptiness — **where the source's cardinality is OWNED somewhere (a sibling guard, a schema, the document's own header), import that owner's count and assert EQUALITY**; a floor is the fallback only where the cardinality is genuinely unbounded. And import the owner's *contract* rather than re-parsing the same document: two parsers over one table is what lets the two readings disagree, and a third parser written to prove they agree is the same defect again. **And the corpus of a repo-wide content scan includes the slice that ADDS it.** The plan record, the ledger line and the pin's own docstring are tracked files, so the new rule grades them from the moment it lands: write them to the rule and check them **before** committing, not after the gate goes red. State the corpus's own limit in the same breath — a tracked-tree corpus sees the working tree and never git history, so a **commit message** is outside every such scan by construction (`docs-traceability.md` → *Change explainability* owns that half). *(0041 Slice 11: the slice's own verdict record had to be authored token-free because the plan file is deliberately unexempted, and a commit message that had already landed carried three of the tokens and had to be amended — the amended-away copy stays in history, unscanned, permanently.)*
- **Auditor checks —** `[D]` Grep the scanners and their tests for `rglob(` / `os.walk(` / a recursive glob rooted at the repo root — each hit is a defect unless it is walking a directory it owns outright. `[D]` Run the sweep in **both** shapes — the maintainer's working checkout **and** a fresh clone or linked worktree — and diff the corpus **sizes**; they must match. `[J]` Does the scan reuse the repo's one enumeration helper, or hand-roll a second that will drift from it? `[D]` Is there a corpus floor assertion, so a too-aggressive exclusion cannot silently empty the sweep? `[J]` Is the chosen convention recorded **at the call site** (a do-not-revert comment), given no gate re-derives it? `[D]` For every set the scan DERIVES from a document, mutate the source so **one** member stops parsing (bold the cell, footnote it, re-case it) and re-run: does the suite go red, or does the set quietly shrink while the scan reports clean? `[D]` Is the derived set's size pinned against a cardinality some other file **owns**, or only against a floor / a non-empty check — which 1-of-N satisfies? `[J]` Does the scan's own docstring claim it delegates to that owner? A stated delegation is an assertion: make it mechanical or delete the claim.
- **Confidence —** `deterministic` — the enumeration method is greppable and the two-shape corpus diff is a measurement, not a judgment.
- **Tradeoff (plain English) —** A disk walk looks identical to the tracked listing on the machine it was written on and diverges on the machines that matter. Because CI clones fresh, this defect **passes CI by construction** and surfaces only in the maintainer's checkout — the one place a release is cut from. `git ls-files` costs one subprocess and makes the sweep's scope a fact about the repo instead of a fact about someone's disk.
- **Incident that motivated this (delete this rule once its cause is gone) —** Plan 0041 Slice 9 (2026-08-17). A new pin enumerated markdown with `Path.rglob` to assert a URL appears in exactly one shipped file. Measured in the maintainer's checkout: **129 `.md` files, 61 of them leaked from linked worktrees under a gitignored `.claude/worktrees/`**, against **60 files and zero leaks** via `git ls-files` — so the pin was GREEN in a worktree, GREEN in CI, and RED only where the land ran. Three scanners in the same repo already used `git ls-files`; the convention was real and written nowhere. The leak is not only worktrees — with every worktree removed, the same walk still picks up 8 untracked `.md` from a vendored virtualenv and a tool cache. *Recurred two slices later — 0041 Slice 11 (2026-08-18), the derived-VOCABULARY half, in a slice whose own spec CITED this dimension. A containment pin derived its forbidden-token set by regex from the document that DEFINES those tokens, and asserted only that the set was non-empty. Bolding **one** cell in that document dropped its token from the alternation, and republishing that token elsewhere then passed the **entire suite** — up to 9 of 10 could vanish with the sibling guard green too, because the sibling counted ROWS, the pin counted format-matching CELLS, and nothing asserted they agree. Killed by importing the sibling's row-count contract and asserting equality — which also made the pin's own "delegates to its sibling" docstring claim true instead of merely asserted.*
- **Sources —** `git ls-files` as the index-anchored listing (git-scm.com); cross-ref *Mutation testing* above (working-tree shape is one of the ambient axes that makes a mutant and the real implementation coincide) and *Exemptions and allowlists* above — an over-broad corpus is the loud twin of an over-broad exemption.

## Forward promises need a tripwire (a strict expected-failure that fires when the promise is KEPT)

- **Good looks like —** When code **registers something ahead of its writer** — a manifest entry, a class annotation, a contract vouching for an artifact a later change will produce — the promise carries a **mechanical expiry**, not only a comment. The cheapest form is a **strict expected-failure test** (`@pytest.mark.xfail(strict=True)`, `it.failing`, an equivalent in your runner) asserting the **fulfilled** state: it is red-as-expected today and turns the suite **red the moment the promise is kept**, forcing whoever lands the later change to delete the marker and the comments that ride with it. The test states both directions — what makes it flip, and what the honest annotation becomes if the promise is **abandoned** instead. **Strictness is the whole point:** a lenient expected-failure passes in both worlds and guards nothing.
- **Auditor checks —** `[D]` Grep the diff for forward-looking registrations and comments (*will*, *once X lands*, *planned*, a TODO naming a future change) — for each, is there a test that **changes state** when the future arrives? `[D]` Is the marker **strict**? `[J]` Does the tripwire assert the *fulfilled* state (so it flips on success) rather than today's state (which flips on nothing)? `[J]` Is the abandonment branch written down — what the annotation becomes if the promised change is dropped?
- **Confidence —** `mixed`
- **Tradeoff (plain English) —** A comment saying "remove this when X lands" is remembered exactly as long as its author is in the room. Three lines of strict expected-failure make the reminder impossible to miss, because the suite delivers it to the person landing X. The cost is one deliberately-red test in the report and the discipline to keep its reason current; the risk is using it as a parking spot for work that should just be finished now. *(Pinning the strictness itself was considered and dropped, 2026-08-14: a meta-test that reads its own source for the decorator argument guards against deliberate vandalism, not against drift — the tripwire's value is the expected-failure flipping when the promise lands, which is intact without it.)*
- **Incident that motivated this (delete this rule once its cause is gone) —** Plan 0041 Slice 4 (2026-08-13): the release/init-contract referential-closure gate accepted a new config path as an "init generates it" output while the init step that writes it was a **later slice of the same plan**. The gate passed on the promise, and the registration's own written instruction — *"if that slice is ever abandoned, re-annotate the class; never leave this claim standing"* — had **no mechanism behind it**: drop the later slice and the gate vouches forever, green, for a file nothing produces. Three lines closed it: a `strict=True` expected-failure asserting the init step documents the path — red today, and red in the other direction the instant init learns to write it. It was taken **together with** the wording fix that stopped asserting a plan-order convention ("no release in between") as a *property* — the mechanical and the verbal halves of one over-claim, and neither half works alone.
- **Sources —** pytest docs, *Skip and xfail* (`strict=True` — an unexpectedly-passing xfail is a failure; `xfail_strict` ini option); cross-ref *Mutation testing* above (a promise nothing can falsify is a test that asserts nothing).

## Coverage of behavior, not vanity %

- **Good looks like —** Tests assert **observable behavior and contracts** (outputs, state transitions, emitted events, error responses), not implementation internals — so they survive refactors and fail only on real regressions. New/changed behavior is covered; coverage % is a *floor signal*, never the goal. No assertion-free "coverage theater" (code executed to light up the line counter with no meaningful `expect`). Tests read as executable spec: arrange/act/assert, one reason to fail each.
- **Auditor checks —** `[J]` Do tests assert outcomes a user/caller cares about, or do they over-specify private internals and mock call-order? `[J]` Any tests that execute code but assert nothing (or only `not throws`) where a real outcome should be checked? (see Test-diff review dimension for the diff-coverage gate) `[J]` Would these tests fail if the behavior silently changed — or only if the implementation is rewritten?
- **Confidence —** `mixed`
- **Tradeoff (plain English) —** Testing what the code *does for the user* catches real bugs and lets you refactor freely; chasing a coverage number rewards tests that run code without checking it and that shatter on every refactor. 100% coverage with weak assertions can be worth less than 70% with sharp ones.
- **Sources —** Martin Fowler, "TestCoverage" (coverage as a tool, not a target) & "Goodhart's Law" framing; *Software Engineering at Google* ch. 11 (behavior over implementation; "test via public APIs"); Google Testing Blog, "Code Coverage Best Practices."

## Test-diff review (did the assertions/coverage get weaker?)

- **Good looks like —** The **test diff is reviewed as carefully as the production diff.** Changes that *weaken* the safety net are caught and justified: assertions loosened or deleted, expected values swapped to match new (possibly wrong) output, tests `skip`/`xit`/`@Disabled`/`it.only`-focused, `try/catch` swallowing a failing assertion, timeouts bumped to mask flakiness, or a golden-master baseline regenerated without explaining the diff. Net coverage and assertion strength on touched areas hold or improve.
- **Auditor checks —** `[D]` Grep the diff for `skip`, `only`, `xit`, `xdescribe`, `@Disabled`, `@Ignore`, `pytest.mark.skip`, `todo`, commented-out assertions, widened tolerances. `[J]` For each removed/loosened assertion or regenerated snapshot: is there a stated, legitimate reason? `[D]` Diff-coverage tool shows changed lines didn't drop below threshold. `[J]` Did an expected value change *to follow* the implementation (rubber-stamping a regression) rather than reflecting an intended behavior change?
- **Confidence —** `mixed`
- **Tradeoff (plain English) —** Reviewing test changes stops the most dangerous move in software — quietly deleting the alarm so the build goes green. It costs reviewer attention on files people skim. Skip it and a real regression ships with a passing suite because someone "fixed" the failing test instead of the bug.
- **Sources —** *Software Engineering at Google* ch. 9 (code review covers tests) & ch. 11; Google Testing Blog, "Testing on the Toilet: Change-Detector Tests Considered Harmful" (Jan 2015, https://testing.googleblog.com/2015/01/testing-on-toilet-change-detector-tests.html) — tests that pass through behavior changes / get rewritten to follow the code are worthless; Fowler, "SelfTestingCode."

## Failure-path & edge-case coverage

- **Good looks like —** Tests cover **the unhappy paths, not just the golden path**: invalid input, boundary values (0, 1, empty, max, off-by-one, negative), nulls/undefined, malformed/oversized payloads, timeouts, dependency failures, partial writes, concurrency/duplicate requests. Error handling is asserted by *behavior* — the right exception type/error shape, the right status, no partial state, the right log/no swallowed exception — matching the Correctness & Reliability standards. Each guard clause and `catch` has a test that drives it.
- **Auditor checks —** `[J]` Are boundaries and invalid inputs tested, or only the typical case? `[J]` Is every error branch / `catch` / fallback exercised and its *effect* asserted (not just "didn't crash")? `[D]` Branch coverage on the changed unit (catches untested error arms). `[J]` Are failure modes of external dependencies simulated (inject timeout/5xx/exception) and the degradation asserted?
- **Confidence —** `mixed`
- **Tradeoff (plain English) —** Most production incidents live on the unhappy path — bad input, a dependency down, a weird boundary — so testing those is where tests earn their keep. It costs more test cases for code that "rarely runs." Skip it and the code works perfectly in the demo and falls over on the first malformed request.
- **Sources —** Boris Beizer, *Software Testing Techniques* (boundary-value & equivalence-class analysis); *Software Engineering at Google* ch. 11; OWASP Web Security Testing Guide (WSTG) v4.2 §4.7 Input Validation Testing (https://owasp.org/www-project-web-security-testing-guide/v42/4-Web_Application_Security_Testing/07-Input_Validation_Testing/) for malformed/hostile-input cases; cross-ref `reliability-resilience` standards.

## Determinism (no flaky tests)

- **Good looks like —** Tests are **deterministic** — same code + same environment → same result, every run, in any order. Sources of nondeterminism are controlled: clock/time is injected or frozen (no `sleep`-then-assert, no real `now()`), randomness is seeded, test order is independent (no shared mutable state/leaked singletons), async is awaited on a condition (poll/await) not a fixed delay, and external I/O is stubbed or pinned. Flaky tests are **quarantined and fixed or deleted**, never left to "rerun until green" or normalize red builds.
- **Auditor checks —** `[D]` Grep for nondeterminism smells: `sleep(`, `setTimeout`-then-assert, unseeded `random`, `Date.now()`/`new Date()`/`time.time()` in assertions, order-dependent fixtures, `@Retry`/`flaky`/`rerun` annotations masking instability. `[J]` Is async synchronized via await/poll on a condition rather than a magic delay? `[D]` Suite passes under randomized order (`--shuffle`/`-p randomly`) and on repeat runs. `[J]` Are known-flaky tests tracked and being fixed, not silently retried?
- **Confidence —** `mixed`
- **Tradeoff (plain English) —** A test that fails randomly is worse than no test — once people see false alarms they stop believing real ones, and the whole suite loses its meaning. Making tests deterministic costs upfront effort (inject the clock, seed the RNG). At Google, as flakiness approaches ~1% the suite starts losing value, so this isn't optional hygiene.
- **Sources —** Google Testing Blog, "Flaky Tests at Google and How We Mitigate Them" (16% of suite flaked at some point) & "Where do our flaky tests come from?"; Martin Fowler, "Eradicating Non-Determinism in Tests"; *Software Engineering at Google* ch. 11.

## Regression & snapshot tests

- **Good looks like —** Every fixed bug ships with a **regression test that fails on the old code and passes on the fix** — the bug cannot silently return. **Snapshot** tests (serialized output, rendered tree, API response shape) are used where output is wide and stable, with snapshots **committed, reviewed, and kept tight** (not giant blobs nobody reads). Snapshot updates are deliberate (`--update` run intentionally, diff inspected) — never reflexively accepted to make CI green.
- **Auditor checks —** `[J]` Does each bug fix include a test that pins the corrected behavior and would have caught the original bug? `[D]` Snapshot files are committed and present in the diff. `[J]` Are snapshots scoped/meaningful (focused on what matters) rather than sprawling captures that get rubber-stamped on update? `[J]` Was a snapshot update in this diff *justified by an intended change*, not a silent regression auto-accepted?
- **Confidence —** `mixed`
- **Tradeoff (plain English) —** A regression test makes a bug fixable *once* — it can't come back unnoticed. Snapshots cheaply lock down large outputs but rot into noise if they're huge and blindly re-approved. The danger is treating "update the snapshot" as a reflex, which quietly accepts whatever broke.
- **Sources —** ISTQB Certified Tester Foundation Level (CTFL) Syllabus v4.0, §2.3 "Confirmation Testing and Regression Testing" (regression test = re-run after a change to catch newly introduced/uncovered defects), corroborated by the ISTQB Glossary "regression testing" entry (glossary.istqb.org); Kent C. Dodds, "Common Mistakes with React Testing Library" (https://kentcdodds.com/blog/common-mistakes-with-react-testing-library) — snapshot anti-patterns; Jest snapshot docs (https://jestjs.io/docs/snapshot-testing) & Vitest snapshot docs (https://vitest.dev/guide/snapshot) ("don't blindly update"); cross-ref Characterization/Golden-master above (a snapshot is a golden master).

## Visual-regression & accessibility testing (UI)

- **Good looks like —** UI changes are guarded by **visual-regression** tests (Playwright/Chromatic/Percy/Storybook) that diff rendered screenshots against an approved baseline across key viewports/themes, so unintended layout/style shifts are caught and intended ones are explicitly approved. **Automated accessibility** checks (axe-core via Playwright/Cypress/Storybook, or `jest-axe`) run on components/pages and fail the build on WCAG violations — understood as a **floor** (Deque's 2021 study found axe-core detects ~57% of issues; traditional tool estimates range from ~30%; see Sources), backed by keyboard-nav and screen-reader/manual checks per the `product-ux` standard.
- **Auditor checks —** `[D]` axe/jest-axe assertions present on changed UI; build fails on new violations. `[D]` Visual baselines committed and diffs reviewed/approved (not auto-accepted). `[J]` Are critical states (loading/empty/error, focus, RTL, dark mode) captured, not just the happy render? `[J]` Is automated a11y treated as a floor with manual keyboard/SR coverage for what scanners miss?
- **Confidence —** `mixed`
- **Tradeoff (plain English) —** Screenshot diffs catch "it looks broken" that unit tests can't see, and axe catches the easy half of accessibility bugs automatically. The cost is baseline maintenance (renders shift, baselines need re-approval) and false diffs from anti-aliasing/timing. Skip it and visual regressions and excluded users ship unnoticed.
- **Sources —** Deque, "Automated Testing Study Identifies 57% of Digital Accessibility Issues" (2021) — https://www.deque.com/blog/automated-testing-study-identifies-57-percent-of-digital-accessibility-issues/ (axe-core, 13,000+ pages, ~300,000 issues); axe-core GitHub (https://github.com/dequelabs/axe-core) — WCAG 2.0/2.1/2.2 A/AA/AAA rule set; Chromatic accessibility-test addon docs (https://www.chromatic.com/docs/accessibility); Playwright axe integration (https://playwright.dev/docs/accessibility-testing); WCAG 2.2 (https://www.w3.org/TR/WCAG22/); cross-ref `product-ux`.

## Contract testing (provider/consumer compatibility)

- **Good looks like —** Across a service/API boundary, **contract tests** verify provider and consumer agree on the wire format *without* a full integrated environment. **Consumer-driven contracts** (Pact + a broker) let the consumer declare expected interactions; the provider verifies the recorded pact against its real implementation, and the broker gates deploy with "can-I-deploy" so a breaking change is caught at build time, not in prod. Schema/contract checks (OpenAPI/JSON-Schema/protobuf back-compat, e.g. Buf breaking-change detection) guard published interfaces, aligned with the `api-and-contracts` standard.
- **Auditor checks —** `[J]` Do changes to a published API/event have a contract test (pact, schema-compat, or stored-response verification) rather than relying on slow brittle end-to-end? `[D]` Provider verification / schema-back-compat check runs in CI and passes; broker "can-I-deploy" green where adopted. `[J]` Is the contract the genuine consumer expectation, kept in sync, not a stale hand-written stub? `[D]` Breaking-change detector (Buf/OpenAPI-diff) gates the published surface.
- **Confidence —** `mixed`
- **Tradeoff (plain English) —** Contract tests catch "you broke my caller" at build time and let independent services deploy without a giant shared test environment. The cost is the broker/tooling and discipline to keep contracts current. Skip it and integration breakages surface only in production, or you pay for slow flaky end-to-end suites to find them.
- **Sources —** Consumer-Driven Contracts — Ian Robinson / Martin Fowler ("ConsumerDrivenContracts"); Pact (docs.pact.io, Pact Broker / can-i-deploy); Buf breaking-change detection; cross-ref `api-and-contracts`.

## Authoring rules (the catalog meta-rules — do not delete)

- **Additive floor:** add dimensions as you discover them; **never delete** one. This catalog is meant to become "every standard we can think of."
- **Right-size:** apply only *relevant* dimensions per change (`KISS`/`YAGNI`); never skip a relevant one. Relevance is a per-change judgment — see `README.md`.
- **Novel patterns allowed** when they add clear value — justify (problem → why existing patterns fall short → benefit) and record in `docs/claugentic-DECISIONS.md`. Unconventional ≠ wrong.
- **Every dimension carries a Confidence tag** so the harness can separate what it *proved* (deterministic gates) from what it *asserts* (judgment). Trust the oracle, not the model's word.
