# Roadmap

The forward backlog for the harness itself. Work runs through `docs/claugentic-WORKFLOW.md` (triage → plan → review → spec → approve → implement → verify → land → retrospect), sliced so each unit lands complete with no tech debt. Tangents land here, never silently into the current change.

> The harness audits *adopter* repos via `/claugentic-dev-harness:audit`, which writes its own `harness-audit:overview` / `harness-audit:backlog` fences into that repo's `docs/claugentic-ROADMAP.md`. This file is the product's own roadmap, not a generated audit — an adopter generates theirs by running the `/claugentic-dev-harness:audit` + `/claugentic-dev-harness:product` gap fences.

> **This is your backlog.** The two fenced sections just below are **regenerated automatically** — `/claugentic-dev-harness:audit` writes the engineering one, `/claugentic-dev-harness:product` gap mode writes the product one; don't hand-edit inside the fences (a re-run overwrites them). ### Later / Ideas

Longer-term tracks and ideas — hand-written, never fence-touched. Deferred harness-maintenance / `doctor` findings ride here with a **`harness`** tag (no separate section). The harness is **feature-complete — there is no open backlog;** new work, if it arises, is surfaced by an audit (the fences above) or added here by hand.

- **`harness`** — audit synthesis-ceiling: auto-size `maxCellsPerRun` + hierarchical per-lens roll-up for very large repos — only when a real repo exceeds the single-pass synthesis ceiling (deferred from the 0025 step-2 audit fix; interleaving already makes a sane-budget pass cover every lens, so this is YAGNI until measured).
- **`harness`** — Stage-2b advisory panel as an `engine/verify.js`-orchestrated path (a `lens-reviewer` plan-design fan-out, mirroring the Stage-7 Verify panel): 2b is prose-convened today and works (advisory, builder-class, 1-round). An engine orchestration would only pay off if a prose 2b proves too unwieldy at scale — YAGNI until then (deferred from 0026 §C; the `lens-reviewer` plan-design *prompt* mode still landed, only the engine orchestration is deferred).
- **`harness`** — **Engineering charter (methodology-aware, not -locked).** A durable per-project *ways-of-working* note — test-first scope (where TDD applies vs test-after) · domain-modeling yes/no · slicing rhythm — chosen once (at `init`/Discuss) and honored by `implementer` + `synthesizer-gate`, so the project **picks an approach and sticks to it** instead of re-deciding per plan. Sibling to `docs/claugentic-PRODUCT.md` (product truth) / the CLAUDE.md harness block (structural truth); records the per-project choice, never imposes one (the universal-harness constraint holds). Closes the "doesn't pick a methodology and stick to it" gap. (User-approved 2026-06-25 re-review; rationale in `docs/claugentic-DECISIONS.md` → The workflow & roles. Watch: keep it lean — risk is over-confining a universal harness.)
  - **First concrete behavior — test-first/TDD.** Make `feature` work test-first *where it earns its place* (logic/domain core yes; spike/UI test-after) via an **independent test-author** (clean-context writes the failing tests; `implementer` greens them unedited). Imports the ONE TDD benefit the harness lacks — *red-first proof the test is meaningful* for features (`bug`/`refactor` already get it; features today lean on post-hoc test review = `[J]` vs red-first ≈ `[D]`). **Encourage now** (model-upheld: implementer prompt + Verify gate, same mechanism as bug/refactor); **enforce only when the named-but-unbuilt red-first/characterization `PreToolUse` hook lands** (never claim enforcement before then). Don't adopt TDD wholesale — the harness already secures its design-pressure / scope-discipline / regression-safety by other means.
- **`harness`** — **Bootstrap-and-approve self-extension ("a software company that specialises in the project").** At onboarding the harness studies the domain and **PROPOSES** a tailored set — the in-scope universal modules + any **domain-specific standard modules** + any **domain specialist agents** — which the **user approves**; Stage 9 then grows it. Extends the existing two-tier promotion **downward** (generate-for-this-repo), not just upward. **Autonomous self-deploy is explicitly out of scope** (collides with the no-over-claim + user-approved-promotion discipline). The largest unrealized piece of the v0.3 vision. (User-approved 2026-06-25 re-review.)
- **`harness`** — **Small standards fills (JIT, not keystone).** Author `architecture-styles` (still reserved), an `error-handling` philosophy module, and a `domain-design`/DDD module **each only when a change pulls it in** — they are *not* the architecture keystone (`maintainability-structure` already cites Clean/Hexagonal/Onion/DDD/Saga/Outbox, and the plan *Architecture & holistic fit* section now frames system-shape up front). Lower priority than the two items above.
- **`harness`** — **Multi-charter / domain-pack ("other types of work" — DIAGNOSED, not built).** A spine-vs-skin study (2026-06-25) confirmed a domain-NEUTRAL **kernel** (the FIND→PRUNE→VERIFY review engine that treats a lens as an opaque doc-path it never parses · the cross-model honesty engine · the 6 reviewer postures · the 10-stage spine · decision-gated autonomy · the ledger trio — the blank `_`-seeds + the existing criteria-mode prove the structure carries no domain) under a swappable **domain-pack** (standards catalog + DoD gate-lists + tag→discipline table + vocabulary + 1–2 specialist agents + an execution binding). "Charter" has **two altitudes**: *methodology* (the engineering charter above — a slot INSIDE the software pack) **⊂** *domain-pack* (re-points the kernel at a non-software domain — this is the "other types of work" ask). Strongest first pack = **deep-research / technical-writing** (the refute-first `finding-verifier` is native to "claim vs cited source"; citation-resolution is a real `[D]` gate, so it isn't gate-poor); data-analysis plausible; PM gate-poor; legal high-consequence; ops too software-adjacent to be a distinct pack. **Hard seam:** the EXECUTION engine (`build-item.js` git-worktree gates, `qa.js` browser-driving) is software-bound — a non-software pack inherits the REVIEW engine free but the EXECUTION engine only via the schema's `manual` fallback. **Sequencing (YAGNI): mature the one software pack + build the engineering charter FIRST**, before promoting domain-pack to a first-class swappable layer. Full rationale: `docs/claugentic-DECISIONS.md` → The workflow & roles.
