# Agent Development Workflow

> ### 👋 New here? Read this first
> This repo is built and maintained with an **agent-assisted workflow**:
> - **Small/local change?** Just make it — tests must pass, and the architecture-tree hook will prompt you to document any new source file in `docs/claugentic-ARCHITECTURE_TREE.md`.
> - **Substantial change?** (new subsystem, cross-cutting refactor, shared-contract change, or **~8+ files**) — don't free-code. The agent **pauses, asks questions, enters plan mode**, and runs the pipeline below: a plan in `.claude/plans/`, an adversarial review, a spec **you approve**, implementation in an isolated branch, verification, then a retrospect that improves this harness.
> - **Your map of the codebase** is `docs/claugentic-ARCHITECTURE_TREE.md` (one line per file) — read it before diving into source. Specialist **roles** live in `.claude/agents/`. **Decisions** → `docs/claugentic-DECISIONS.md`. **Backlog** → `docs/claugentic-ROADMAP.md`.
> - **Build mode** (`skills/build/SKILL.md`) **auto-drives this pipeline over the audit backlog** — pick items or a whole tier, pausing only at the decisions that are yours.

> ### Adopter note — reading this doc inside YOUR repo (not the harness)
> This WORKFLOW is a **managed copy** in your `docs/`, so a few references resolve to the **installed plugin**, not to files your repo contains:
> - **The specialist agents and the `engine/*.js` scripts** live **inside the installed plugin** — agents resolve at spawn by their namespaced id, engine scripts run via the Workflow tool from the install path. They are **NOT** a `.claude/agents/` or `engine/` directory your repo must provide.
> - **The Definition of Done's *deterministic gates* mean THIS project's OWN gates** — *your* lint, type-check and test suite — plus the architecture-tree and doc-budget checks `init` delivers. Of the commands below, `python -m pytest` is the **harness's own** suite (**substitute your project's equivalent**) and `python scripts/check_versions_synced.py` is **harness-self** (it compares the *plugin's* two manifest versions). `python scripts/claugentic-check_doc_budgets.py` is the one that is **not** harness-self — it measures whichever repo it sits in, against that repo's own `.claude/claugentic-doc-budgets.json` (no config = exit 0, nothing measured). **Payload membership and repo-local presence are two facts:** it rides the release payload AND `init` delivers a copy into your `scripts/`, chaining it into your pre-commit wrapper where one is wired — so the command resolves in **your** project once `init` has run there, and only then; elsewhere `/doctor`'s budget advisory (same caps config) is your signal. **Never run the plugin's own copy from your repo:** every gate script anchors to its own checkout, so its verdict is about the plugin clone.
> - **The architecture-tree check is hook-wired by `init` only when the tree-gate is enabled** — a fresh or mature-no-tree repo gets a harness-format tree and the hook; a mature repo with its own tree is **asked** (replace → gate on; keep yours → **gate off, no hook**). Gate off: run `scripts/claugentic-check_architecture_tree.py` (`python` / `python3` / `py`) by hand at Verify.
> - **Three managed-file kinds** (governs what ships + what `init` recreates): **full-copy docs** (this WORKFLOW, PLAYBOOK, the standards modules) — source = ship = your copy, refreshed on re-`init`; **repeated-use templates** (`*_TEMPLATE.md`) — copy one per use, also refreshed; **one-time seeds** (`_X.md` → `X.md`) — copied **with the underscore stripped, create-if-absent only**, never refreshed (it would clobber the ledger you fill over time). A file the release strips but the workflow needs in any repo must fall into one of these (the release/init contract).
> - **Growing the harness happens upstream, not in your copies.** New roles, standards edits and workflow changes are edits to the **plugin** (*The learning loop* names the channel); editing your managed copy lasts only until the next re-`init`. Lessons about YOUR OWN codebase stay local.

How agents **and** human devs take *substantial* work from idea → landed change while keeping quality high and the harness self-improving. This is the source of truth for process.

> **One-line:** Triage → Discuss → Plan → Review the plan → Spec → **Approve** → Implement → Verify → Land → **Retrospect**. Small changes skip to Implement+Verify.

## 0. Triage — does this need the full pipeline?

**The *substantial* triggers** (referenced throughout — the effort-dial, the Verify fan-out and the 2b panel all fire on this same list): a new subsystem · a cross-cutting refactor · a change to a shared contract/pattern/standard · a security/trust boundary · any trust/honesty surface · **roughly 8+ files**. Those take the **full pipeline**. **Lightweight path** for small/local/mechanical changes: straight to **Implement → Verify**, still updating `claugentic-ARCHITECTURE_TREE.md` and `claugentic-DECISIONS.md`. When unsure, default to full; the `synthesizer-gate` (Stage 3, plan-gate) confirms the path was right.

**Triage continuously, not just up front.** A conversation often *grows* into a substantial change. The moment a request is shaping up to cross that bar, **stop free-coding**: ask clarifying questions — technical *and* **product-discovery** (Stage 1) — until scope is crystal-clear, then **enter plan mode (Stage 2)**.

**Carry-forward gate (before a new arc).** Before opening a new substantial plan, confirm the **prior** arc left nothing un-homed — every finding it deferred or left open now sits in its proper place (dispositions: *Plan file lifecycle*). The **proactive** complement to the close-time disposition rule and doctor's retroactive plan-scan: it catches a prior plan that closed imperfectly *before* new work builds on top. **Model-upheld** — findings are prose, so no mechanical gate (doctor is the retroactive net). Lightweight-path changes skip it.

**Mirror the ask back before you build (shape-triggered, either path).** When a request arrives as rambling multi-clause prose — several asks chained, constraints buried mid-sentence, no single "the ask is X" — distil it **inline** (*goal · scope · the constraints you caught · the questions actually asked*) and mirror it back for a yes **before any substantive work**; **never proceed on inferred scope without stating it.** Triggered by input **shape, not size**, so unlike the carry-forward gate it applies on **either path**, and it is load-bearing before anything irreversible (a history rewrite, a force-push, a large delete). Stage 1 clarifies *outward*; this restates *inward* for a yes — the intake-time counterpart of the Stage-4→5 confirm-back, catching a misread at turn one. Ephemeral and inline; no persisted artifact. **Model-upheld** — no hook can grade a restatement.

## Principles (apply at every stage)

- **Slice small, land complete.** Every unit of work must be finishable by **one specialist agent in one session, no hand-off** and land **vertically complete** — no half-done state, no `TODO`/debt left behind. If it doesn't fit, decompose *before* implementing. Reviewer-upheld — nothing mechanical checks slice size.
- **No new tech debt.** A landed slice leaves the codebase at least as clean as it found it: tests added, ARCHITECTURE_TREE updated, no dead code, no silenced errors.
- **The harness is living.** Any task may improve STANDARDS / CLAUDE.md / the `.claude/agents/` library / this workflow. Stage 9 is how; treat harness improvements as first-class output.
- **Delegate liberally.** Use subagents freely and in parallel — **no resource constraints** — so the orchestrator's context stays lean for synthesis and decisions.
- **Effort-dial the machine.** Scale review depth to risk and size, and load only the standards modules the change *touches*. The dial flips on the **Stage-0 *substantial* triggers**: below them, a quick **solo `synthesizer-gate`** look; at any of them, fan out the lenses (and, on a trust surface, the diverse panel). Running the whole machine on a trivial change is how a harness kills the velocity it exists to protect.
- **Diverse critics on contested or trust-surface changes.** A contested design fork OR a trust/honesty surface (claims, `[D]`/`[J]` labels, proof-vs-attempt wording, a security boundary) triggers the **diverse panel** — `synthesizer-gate` + `yagni-sentinel` + `honesty-reviewer`, **plus `product-designer` when user-facing** — at **every gate that change passes** (Plan **and** Verify); else a lone reviewer suffices. At **Verify** the wired mechanism is `engine/verify.js`: the orchestrator **invokes** it (model-upheld — the platform does not auto-fire workflows) and the script convenes the panel mechanically; unavailable → say so, convene in prose, tag the run **"prose-orchestrated"** — never claim script guarantees on a prose run. At **Plan** it is the **advisory Stage-2b deep-dive** — **builder-class: it CONTRIBUTES, it does not gate.**
- **Review is cross-review by separate specialist agents, each clean-context.** The gate/refute roles — `synthesizer-gate` · `honesty-reviewer` · `finding-verifier` — are **distinct agents**; each works only from `{claim, file:line, …}` and **never sees the builder's rationale or transcript**, so it cannot rubber-stamp the reasoning. The independence is of **context and role**, **not** of model: blind spots can correlate, and the harness does **not** claim model-independent review. **Honest claim:** multiple skeptical, clean-context passes — a reduction of rubber-stamping risk, never a guarantee. *(The engine computes `crossModel` from the judges' own self-reports; in a single-session run judge and builder are the same family, so `crossModel: true` is effectively unreachable and the same-model disclosure fires — running the review on a different tier is the one control that works.)* **Every judged run SAYS that outcome out loud, never only into its JSON:** `audit`/`product` render it into the backlog's run-report line; **verify · QA · build** state the returned `crossModel` **verbatim** in the report the user reads whenever it is not `confirmed` (`engine/verify.js` → `crossModel.tag`; `engine/qa.js` · `engine/build-item.js` → the `crossModel` string). A clean "panel passed" with the disclosure left in the result object is the over-claim this reporter exists to prevent.
- **No model is named anywhere** — a judge inherits the session's tier, and any substitution made at the spawn site is disclosed in that run's own `RUNNING AS:` line.
- **The optional engineering charter** (`docs/claugentic-CHARTER.md`) is a **living per-work-type record** — it records the approach chosen per kind of work (from the methodology toolbox below) and **applies** it when that kind recurs; it **defaults to the toolbox judgment**, so an **empty charter ≡ current behavior** (deleting the file also means deleting its caps-config line — the budget gate fail-louds on a missing budgeted file). Optional, model-upheld, revisable-default-not-mandate.
- Plus the CLAUDE.md non-negotiables: SOLID > DRY > KISS > YAGNI · fail loudly · validate at boundaries · configurable-over-hardcoded · single source of truth.

## Context & handoff

**The durable memory is the plan file + `claugentic-DECISIONS.md` + `claugentic-ARCHITECTURE_TREE.md`** — keep them current as you go. For long work a **fresh session resuming from the plan checklist beats a deeply-compacted context**; no manual "handover" is needed.

## Roles — a library mapped to functions, not a fixed pair

The orchestrator **selects the role(s) that fit the task**, spawning several or composing them; it is not locked to a fixed sequence.

**Native Claude capability does the creation.** Drafting a **plan** and **implementing** a slice are **native** work the harness merely *enables* (the spec contract + the `docs/claugentic-PLAN_TEMPLATE.md` architect-pass forcing function + worktree isolation) — **do not wrap generation in a vanity "architect" agent**: the architectural thinking comes from the TEMPLATE's *Architecture & holistic fit* section + the standards lenses, not a label. Roles map to **functions** — *generate* (native) · *apply a lens* · *critique* · *gate* · *product* — and agents **point at** the standards catalog, never duplicate it (DRY).

Starter library (`.claude/agents/`):
- **`implementer`** — builds one approved slice complete, in an isolated worktree, to the in-scope standards.
- **`synthesizer-gate`** — the integrate→verdict→loop **gate**; three caller contracts: plan-gate · verify-verdict · audit-synthesis.
- **`lens-reviewer`** — applies **one** lens (a standards module, the whole scope, or one acceptance criterion); modes verify-diff · audit-scope · whole-scope · plan-design · product-gap.
- **`product-designer`** — the product/UX lens; modes discover (Stage 1) · elevate (spec critique).
- **`finding-verifier`** — refutes **one** finding from the claim + `file:line` alone, never the finder's rationale.
- **`yagni-sentinel`** — the anti-over-engineering skeptic; argues a plan/diff is *too much*.
- **`honesty-reviewer`** — the over-claim lens; refutes **copy**, not code.
- **`retrospect-harvester`** — runs the Stage-9 harvest over a landed slice; returns the edits, or "nothing durable".
- **`runtime-qa`** — drives the **running** app to verify **one** acceptance criterion; tags outcomes, never fakes one.

Also available without new files: built-in **`Explore`** (fan-out search), **`Plan`** (drafting), and `/code-review` · `/simplify` for diff cleanup. **Add new role files as needs emerge** (Stage 9).

### Why the multi-agent shape — the dynamic-workflow grounding

The `engine/*.js` + the Workflow tool *are* a **dynamic workflow** — Claude writing its own multi-agent harness on the fly (it pairs with the `/loop`-`/goal` primitives — see *Bundled edge-skills*). The rationale for the shape is the three single-context failure modes, each **structurally mitigated, never "solved" — grounding, NOT proof**: **agentic laziness** → build-to-green, the DoD gate list, loop-until-dry, the "not-green at cap → here's the residual, nothing partial lands" honesty, the **independent Verify gate** · **self-preferential bias** → clean-context independent reviewers (`finding-verifier` gets only the claim + `file:line`; the Verify panel is never handed the builder's rationale) · **goal drift** → the plan file + spec as durable memory, machine-readable acceptance criteria, the re-confirmed worklist order.

**Pattern map (accurate, not aspirational):** **fan-out-and-synthesize ✓** (the audit's lens fan-out + the Verify panel) · **adversarial verification ✓** (`finding-verifier` + `honesty-reviewer`) · **loop-until-done ✓** (build-to-green + loop-until-dry) · **generate-and-filter ✓** (audit → verifier/prune → backlog) · **classify-and-act ~partial** (the tag→discipline routing) · **tournament ✗ — NOT embodied**: the pipeline runs no N-solution pairwise-judged tournament (reachable via the Workflow tool's judge-panel pattern if a maintainer wants it; the pipeline itself does not).

## The pipeline

**The ten stages group into four beats — `FRAME → APPROVE → BUILD → CLOSE`** (a one-glance map; no stage is cut or renumbered): **FRAME** (0 Triage · 1 Discuss · 2 Plan · 3 Review · 4 Spec) converges on *what to build and how* · **APPROVE** (5) is the user's sign-off, *no code before this* · **BUILD** (6 Implement · 7 Verify) · **CLOSE** (8 Land · 9 Retrospect) ships it and harvests the lessons.

| # | Stage | Beat | Owner | Output |
|---|-------|------|-------|--------|
| 0 | **Triage** | FRAME | orchestrator | full vs lightweight path |
| 1 | **Discuss & brainstorm** | FRAME | orchestrator + **user** | learn the endeavour from multiple **angles** before planning — technical scope **+ product-discovery** (who's the user · the job-to-be-done · what success/"delight" looks like · the key flows & their states), which surface the user-story gaps a technical-only intake misses. User-facing work pulls in `product-designer`; the orchestrator writes `docs/claugentic-PRODUCT.md`. Tangents→ROADMAP, decisions→DECISIONS |
| 2 | **Draft plan** | FRAME | orchestrator / `Plan` (+ advisory panel) | `.claude/plans/NNNN-<slug>.md` (Problem · Approach · **Architecture & holistic fit** · Risks · Test strategy · slices — Review & Spec filled later), **sliced into ≤1-session units**; substantial work runs **2a → 2b → 2c** |
| 3 | **Review the plan** | FRAME | `synthesizer-gate` (plan-gate altitude) | critique written into the plan's *Review* section; iterate until it passes the gate |
| 4 | **Spec** | FRAME | orchestrator | plan upgraded to implementation-ready spec **per slice**: the plain-English block (below), then file-by-file changes, signatures, test list, acceptance criteria, **+ the in-scope `docs/claugentic-standards/` dimensions & target bar (entry: `docs/claugentic-ENGINEERING_STANDARDS.md`)** |
| 5 | **Approval gate** | APPROVE | **user** | sign-off on the spec — *no code before this* |
| 6 | **Implement** | BUILD | `implementer` | one slice/session, isolated worktree/branch; upholds CLAUDE.md; updates ARCHITECTURE_TREE inline |
| 7 | **Verify** | BUILD | `synthesizer-gate` (+ lenses) | **effort-dialed** on the Stage-0 *substantial* triggers: a **small/local** change → `synthesizer-gate` solo; any trigger → fan out the panel via **`engine/verify.js`**, invoked by the orchestrator (`${CLAUDE_PLUGIN_ROOT}/engine/verify.js` for an adopter, the repo-local `./engine/verify.js` here) — one `lens-reviewer` per relevant `docs/claugentic-standards/` module **+** `yagni-sentinel` (**+ `honesty-reviewer`** on a trust surface), then `synthesizer-gate` **synthesizes**, same-model tag computed in code — **say that tag out loud when it is not `confirmed`, never leave it in the JSON**. Workflow tool unavailable → prose, tagged **"prose-orchestrated."** **All Definition-of-Done gates green**; run **`/simplify`** + **`/code-review`**; confirm spec match. Findings are **dual-layer** (technical + plain-English). |
| 8 | **Land** | CLOSE | orchestrator | conventional commit/PR; delete the completed plan (git history keeps it); append DECISIONS |
| 9 | **Retrospect & evolve** | CLOSE | orchestrator | harvest learnings into the harness (see below) |

**Stage 3 gate — a plan may not pass review until:** it is correct & sound (SOLID/patterns), each slice is **session-sized and lands complete with no debt**, the right path was chosen, risks + test strategy are stated, **Architecture & holistic fit** is genuinely reasoned (substantial work), and any harness impact (new STANDARD/agent/doc) is noted. The reviewer writes a verdict + required changes into the plan; the orchestrator iterates.

**Stage 2, the architect-pass mandate.** Because architecture is **model-upheld**, `docs/claugentic-PLAN_TEMPLATE.md` carries a required **Architecture & holistic fit** section the Stage-2 draft **must fill for substantial work**: codebase fit (layering · module placement · design patterns · SOLID/SoC) · product fit · the **quality dimensions to uphold, each mapped to its `docs/claugentic-standards/` module** (the forward-pointer the Stage-4 Spec's *in-scope dimensions* refines per slice) · future-proofing — plus, for **user-facing work**, the **felt/visual craft bar** the surface must clear. **Initial framing, NOT the deep per-slice Spec** (that stays JIT), and it GUIDES every downstream agent. **Enforcement = structural prompt + review, NOT a mechanical gate:** the template forces the section to *exist*, `synthesizer-gate` audits it is genuinely reasoned, `yagni-sentinel` guards the over-build edge. Trivial changes may one-line or skip it.

**Stage 2, an optional ADR working-artifact for a weighty design fork (`/architecture`).** For a fork with real trade-offs a fresh reader would need reasoning-out, **consider** the bundled `/architecture` skill for an ADR as a **Stage-2 working artifact**, then **distil ONE `claugentic-DECISIONS.md` line at Land** (the ADR is scaffolding, not a shipped doc). A **model-upheld option, never wired behavior** — most forks are reasoned inline in *Architecture & holistic fit*, and ADRs are **not** always-loaded docs.

**Stage 2, the draft → advisory-panel → incorporate sub-process (*substantial* work):** three steps, so the diverse-panel-at-Plan is a **standard** step, not an afterthought. **Stage 3 (Review) stays the gate, unchanged.**

- **2a — Draft.** The orchestrator drafts in **plan mode** (the built-in `Plan`) → a plan file **structured by `docs/claugentic-PLAN_TEMPLATE.md`**, with **Architecture & holistic fit** filled.
- **2b — Specialist advisory deep-dive (ADVISORY, builder-class — contributes, does NOT gate).** A **scoped panel** reviews the draft's **design**: the **in-scope `docs/claugentic-standards/` lenses** (relevance-gated; each `lens-reviewer` in its **plan-design** mode) **+** `yagni-sentinel` (too much?) and `honesty-reviewer` (do the claims over-state?) **+ `product-designer` when user-facing**. **Prose-convened** — there is **no engine path** (a **deferred ROADMAP item** — YAGNI for a 1-round advisory panel that works in prose today). Its feedback is input to 2c, not a verdict.
- **2c — Incorporate.** The planner folds the feedback into a **refined plan**. The **2b↔2c loop is bounded — 1 round by default**: advisory feedback has no natural stop, so the planner decides whether a second round genuinely adds value rather than looping for polish. Then **Stage 3 Review** → Stage 5 Approve.

**Same panel, two altitudes (HONEST framing):** most of these lenses reappear at **Stage 7 Verify** — but there they review **code** and **GATE** (a `CHANGES_REQUIRED` blocks the land), whereas at **2b** they review **design** and only **CONTRIBUTE**. 2b is **model-upheld, builder-class**: it does not mechanically improve the plan, and Stage 3 remains the only Stage-2/3 gate. **2b fires on the substantial triggers only.**

**Stage 7, the whole-feature closing pass (last slice of a multi-slice plan):** each slice's Verify checks *that slice's diff*, so cross-slice integration regressions fall between the per-slice gates. On the **last slice of a multi-slice plan** the Verify pass ALSO confirms the **assembled feature achieves the Stage-1 job-to-be-done**, end-to-end. **Model-upheld, orchestrator-driven** — `engine/verify.js` is sandboxed and **cannot read `docs/claugentic-PRODUCT.md` / the plan off disk**, so the *orchestrator* passes the job-to-be-done (and "this is the closing pass") into the last-slice `synthesizer-gate` prompt; the engine gains **no new args-contract field** (KISS). Single-slice changes skip it.

**Stage 7, when the SPEC is what's wrong (the spec-amendment path).** Sometimes the diff matches the spec faithfully and the **spec line is the defect**. A **spec-conformant diff is never a defense against a lens finding**: the finding stands, and the *spec* is amended. Record a short **`Spec amendment`** note in the plan file (*the line as spec'd · the corrected line · the lens and the reason*), fix the diff in the same pass, and restate any acceptance criterion it touched. Four rules, all **model-upheld**:

- **Tighten vs re-scope.** An amendment that only **tightens** what the user already accepted (a narrower permission, a stricter guard, a stronger assertion) rides the Verify loop; one that changes **scope, a stated trade-off, or the risk profile signed off at Stage 5** goes **back to the user**. *(0041 S2: the spec prescribed workflow-level `permissions: contents: write`, the security lens refuted it; amended to `contents: read` + `write` on the `publish` job — a tightening, no re-approval.)*
- **Prefer fixing the MECHANISM over weakening the COPY.** Tightening keeps the Stage-5 promise intact and rides the loop; rewording the promise to match the defect changes what the user approved. *(0041 S3: reserving a clause budget tightened the guarantee; softening "open **any** adopter repo …" to "usually" would have needed re-approval.)*
- **An acceptance criterion is read for what it PROMISED — never used as a veto on a correctness fix.** State the AC's **actual scope** and check whether the fix touches it; do not soften the fix to preserve its letter. *(0041 S4: read literally, a byte-equivalence AC would have preserved a gate printing "all managed ledgers within budget" over a file at 52× its cap.)*
- **An amendment that outlives the plan is a Stage-9 row-(a) promotion.** Plans die at close, so ask whether the corrected line is about *this slice* or about *how specs are written*; route a general one to the standards module or role file that owns the topic. *(0041 S10a: "a normalizer that N call sites collapse onto must be a fixed point.")*

**Stage 4 → 5, the plain-English layer (the non-engineer's steering wheel):** the spec is code-shaped, but approval is about *intent, not code*. Every spec **MUST open with a short plain-English block — *what this builds · what "done" means for you · what you're accepting (risks/trade-offs)*** — **presented first at Stage 5**, with the file-by-file detail beneath it. *(`docs/claugentic-PLAN_TEMPLATE.md` carries a matching section.)*

**Stage 4, the charter write-trigger (defaults-safe).** **IF this spec names a methodology approach that DIFFERS from the default grain for this work-type** (e.g. test-first chosen for a `feature`) — **RECORD it to `docs/claugentic-CHARTER.md`** per the charter's RECORD/GROW behaviors (`work-type → chosen approach + brief rationale`, **updating that work-type's entry in place, never appending**). **Fires ONLY on a non-default choice: default-grain work writes NOTHING** — an empty charter still ≡ default behavior. A **model-upheld prompt, not a gate**. *(Behavior contract: `docs/claugentic-_CHARTER.md`.)*

**Stage 4, scoping the in-scope dimensions (surfaces, not just runtime output):** a dimension is in scope for **every surface the slice WRITES** — code, docstrings, skill/README copy, index and ledger entries, and the plain-English approval block itself — never for its runtime output alone. Narrowing a dimension at spec time narrows what the Verify panel is asked to check, and copy is the surface a slice most often ships un-reviewed. *(0041 S5: honesty was scoped to "the wrapper's printed claims"; the hardest finding was a line written into every teammate's always-loaded `CLAUDE.md` telling husky users to run a command that would disable their own hooks.)* **Second axis — a defect whose SYMPTOM is a false claim puts `honesty` in scope, whatever file it lives in.** Scope from the slice's **defect list**, not its file list. *(0041 S10a: the spec called the slice "no trust-surface interaction" while its own second defect was the run reporting cross-model review it had not received.)*

**Stage 1, the plain-English open (say why before the questions):** *"Before any code I'll ask a few questions about who this is for and what 'good' looks like; your answers steer everything downstream."* Then ask.

**Keep the docs current — it's part of each stage:**
- **Implement (6):** update `claugentic-ARCHITECTURE_TREE.md` for any file add/move/remove (also hook-nudged); touch `CLAUDE.md` only for a genuinely new gotcha/command/pattern — *index, don't duplicate code*.
- **Verify (7) — honesty register:** the report says what the verify **attempted and tagged**, never what it "proved." Deterministic gates passed; reviewer sign-offs are model-upheld judgment, not a guarantee.
- **Land (8):** file a dated one-liner into the fitting `docs/claugentic-decisions/` shard for non-trivial choices (`docs/claugentic-DECISIONS.md` is an INDEX — never append to it); update `ROADMAP.md` if scope shifted; **reconcile the plan's header with its own tail** — the next session reads Status / Resumable-from / Blockers as fact, so an obligation the body leaves open is a **Blocker** there, never a "none"; **run the Stage-9 harvest checklist** before moving on.
- **Land (8) — worktree hygiene:** a slice that **landed, was abandoned, or was escalated** leaves its worktree **clean or disposed** — the **branch is the durable artifact**, so an unchanged worktree is auto-reclaimed and a changed one is landed (then reclaimed) or deliberately kept for inspection, never silently orphaned. (*Disposition* covers the work; this the *worktree* it lived in.)
- **Land (8) — honesty register:** the close-out names **which gate-class passed** — the *deterministic gates* vs the *reviewer sign-offs* — never a blanket "verified/done."
- **Land (8) — the numbers you quote are the MERGE tree's, not the branch's.** Byte budgets, index currency and gate verdicts all change **at the merge**: two branches can each sit under a cap while their merge sits over it. Measure the **merge result before you commit it** — `git merge-tree --write-tree <a> <b>`, materialize it (`git archive`), run the gates there — and quote **those** numbers. **Do not count on the commit hook:** a conflict-free `git merge` goes through git's `pre-merge-commit` hook, which `init` writes (delegating to the same wrapper), so the chained gates fire there in a repo re-`init`'d at v0.5.3+; a server-side PR merge runs no local hook at all, and a CI job measuring the merge ref still lets an **advisory** (a WARN, exit 0) land green inside a passing log. *(0041 S7: two branches appended to one budgeted shard; the merge measured 12,610 B against a 12,600 WARN neither branch tripped.)*
- **Land (8) — close out for the user:** say it plainly — *"This one's done. Next: pick another item the same way, run `/claugentic-dev-harness:build` to keep working the backlog, or re-run `/claugentic-dev-harness:audit` for a fresh picture — you're finished when Tier 1 and Tier 2 come back empty."*
- **Retrospect (9):** promote durable learnings into the `docs/claugentic-standards/` modules (entry: `docs/claugentic-ENGINEERING_STANDARDS.md`) / `CLAUDE.md` / agent files.

## Definition of Done

A slice is **done** — and may land (Stage 8) — only when **all** hold. Two groups, same bar, differing in *who* says pass.

**Deterministic gates** (pass/fail, can't be argued around):

> **Run each gate as its own command and read its exit code — never pipe one through `tail`/`head`/`grep`.** A pipeline's status is the **last** command's, so `<gate> | tail -1` reports the *filter's* success and a red gate reads green. Trim noise by reading the output, not by piping. *(2026-08-13: a real failure of the shipped-content scan below was masked exactly this way at Land. A per-gate-step CI job is immune by construction; this bites the local pre-push run.)*

1. **Full test suite green** + any regression/snapshot tests — *your* project's suite. *(This plugin's own suite is `python -m pytest`.)*
2. **Architecture-tree check green** (when the gate is wired) — file-index presence, staleness, and **glob-drift detection**. Run it with whichever interpreter you have (`python` / `python3` / `py`): `scripts/claugentic-check_architecture_tree.py`.
   - **Glob drift is the handled case.** When the gate reports watching no files while the repo now contains source, say so plainly — *"I'm updating your codebase map to match your new code"* — then re-detect the layout and reset `INCLUDE_GLOBS` (init step 5's terminating self-correction). **Scope the claim honestly:** only this *handled* path reads as plain English; a **genuine gate crash still fails loud by design**.
3. **Version-sync green** — *harness-self only* (developing this plugin): `python scripts/check_versions_synced.py` enforces `plugin.json` ↔ `marketplace.json` version equality (`plugin.json` is the source of truth). A **run-gate**, not hook-wired; scope is the two manifest versions only. **Not applicable to adopter repos** — skip it.
4. **Doc-budget green** — every budgeted managed ledger (`CLAUDE.md`, `claugentic-DECISIONS.md`, `claugentic-ROADMAP.md`, `claugentic-INVARIANTS.md` — plus `claugentic-WORKFLOW.md` **harness-self only**: in an adopter repo WORKFLOW is a managed full-copy you don't author, and the caps seed deliberately never caps it — and, where one has been split, each part under a shared per-part cap) stays within the byte budget **your repo's own caps config declares**: `python scripts/claugentic-check_doc_budgets.py` (where it resolves in an adopter repo: the *Adopter note* above). The gate holds no caps of its own — it reads `.claude/claugentic-doc-budgets.json`, and an **ABSENT config is a deliberate quiet no-op** (exit 0, nothing measured), so it binds exactly as far as the caps you have written. **The budget is BYTES** (`len(read_bytes())`), **not characters** — a middot-dense ledger reads a few % lower by `wc -m`, so judge the % from the gate's byte figure (a recurring mis-measure). **Hook-chained:** `init` chains it into the shared pre-commit wrapper right after the tree check and writes the `pre-merge-commit` sibling delegating to the same wrapper — so where that wrapper is wired it runs at commit time **and, since v0.5.3, on a conflict-free `git merge`**, and a gate added later covers merges automatically (positive pins in the harness's own suite keep the chaining and the hook's executable mode true). Where no wrapper is wired — a tree-gate-off repo, or no working Python — it stays a run-gate you invoke, and this repo's CI runs it on every push and at every tag. It emits a **WARN at ≥90%** (the cue to condense — absorb landed build-records first, then superseded entries, to git history) and fails only on a strict breach.
   - **The condensation pass — condense on the trigger (model-upheld).** A **≥90% WARN**, or `/doctor`'s **"condense soon"** advisory, is a **do-it-now signal, not a deferral**: run the pass inside **the current slice**. **The executable operator is `/claugentic-dev-harness:condense`, which owns the procedure — this doc does not restate it**; the Definition of Done **OFFERs** it on a WARN or breach, so a budget signal is a **ramp to the operator, never a dead-end**. **An inline pass is safe** — the drop is git-recoverable — so a small one rides the slice as a reversible FLAG; surface the diff first when it is large or surprising (always with `/condense`, whose apply is gated on your approval).
     - **The escape-valve ladder — when condensation genuinely can't reach the band (the content is ALL live).** `/condense`'s lever order is *how to cut*; this ladder is *what to do when cutting is exhausted.* **Do NOT over-cut live rules to fake the band** — climb these in order:
       1. **Promote durable constraints to their proper home.** A must-hold that has hardened into a load-bearing invariant belongs in `claugentic-INVARIANTS.md`; durable structural/domain context belongs in the relevant `CLAUDE.md` harness block — moving it out is real reduction, not deletion. **Promoting respects THEIR caps too** (a cascade, not a loop): promote the distilled constraint, never the narrative; if the target home is *itself* near its cap, the constraint set has genuinely grown — go to rung 2. Not a licence to relocate bloat.
       2. **A deliberate, RECORDED cap increase — the honest escape valve.** When the content is genuinely all-live and promotion can't move it, **raise this repo's cap for that file** rather than shave a live constraint: a one-line edit to `.claude/claugentic-doc-budgets.json` **PLUS a dated one-line decisions entry recording why the cap grew** (filed into the fitting shard via the `docs/claugentic-DECISIONS.md` index, never appended to the index). A `[J]` **recorded decision, never a mechanical action** — git holds the prior cap, the DECISIONS line holds the *why*. Raising a cap without that rationale is what this rung forbids. *(**One cap source per repo**, read by both the gate and `/doctor`'s advisory — with **one harness-self extra**: this repo also pins its caps byte-exactly in a test, so a bump updates that pin in the same commit. Its **schema**, all three entry forms, is `skills/doctor/SKILL.md` → *Adopter doc-budget advisory*. Never a second cap list.)*
       3. **Shard the ledger — the LAST resort (built, and climbed once).** Split an oversized ledger into a routing **index at the original path** plus one file per topic, each under its own cap. Not reached first: for an **append-style log** (entries supersede, so condensation reclaims bytes) a recorded cap-bump preserves the single-scannable-record property; sharding earns its keep on a **rule-book** whose entries persist by design, where each pass lands higher than the last. Two properties make the split safe: every external reference keeps pointing at the **index path**, and the index stays **routing-only** under a tight cap — an index that starts holding entries has quietly become the ledger again. **Adopters are unaffected by default**; one who climbs this rung caps each part in their own config, the procedure `skills/doctor/SKILL.md` owns.
5. **Shipped-content scan green** — *harness-self only* (developing this plugin): `python scripts/check_shipped_content.py` scans every SHIPPED file's text for release/init-contract breaches — a stranded `claugentic-dev-harness:<token>` namespace literal (a rename leaving a dead agent/skill/command id) or a dangling reference to a stripped-uncreated path. A **run-gate**, not hook-wired; it pins the **exact-literal** cases mechanically (hard exit 1) and only **WARN**s on the heuristic uncaveated-gate-mention pass. The script is **stripped from the release**. **Not applicable to adopter repos** — skip it.
6. **The project's lint / type-check / security gates** green.

**Reviewer sign-offs** (model judgment, not a mechanical gate):

1. **In-scope `docs/claugentic-standards/` dimensions pass** the `synthesizer-gate` audit (incl. SOLID) — solo, or synthesized from `lens-reviewer`s + `yagni-sentinel` — for what this slice touches; `/simplify` + `/code-review` run — **or each is discharged in the plan's `Flags:` line with its reason**: a review a panel lens already performed *with measurements*, or an auto-apply pass over an artifact whose exact bytes a recorded measurement attests (changing them un-verifies it), is **discharged**, never silently skipped; a helper that **dies mid-run** is discharged only by the angles it completed, each named. *(0044 S1a: an auto-apply simplification pass was skipped on a calibration-locked instrument — the yagni and maintainability lenses had done that review with measurements; the code-review helper's cross-file tracer died unreported and was discharged via its one completed angle.)* For **any user-facing surface** the craft dimensions (`product-ux.md` → *Aesthetic & motion craft*) are **in-scope** (effort-dialed — the named craft bar is reviewed, never certified beautiful).
2. **Runtime QA (dial-gated)** — when the slice's spec carries acceptance criteria (the `docs/claugentic-PRODUCT_SPEC.md` schema), the repo records a run-the-app command, and the Verify dial has fanned out: `engine/qa.js` attempts each criterion's flow in the running app and tags the outcome (screenshots on failure); findings join the Verify synthesis. The script sequences the attempts and never silently skips (a QA run that could not boot the app reports exactly that); invoking it, and the flow observations, are model-upheld.

## Decision-gated autonomy (when to stop, when to proceed)

While iterating to the bar above, the agent **proceeds autonomously by default** and **stops only for a decision that is genuinely the user's** — the question is never "which rung am I on," it is **"is this a real choice the user must make?"** **MODEL-UPHELD, not a mechanical gate:** nothing forces a stop at the right moment. A mis-judgment is **bounded by flag-and-surface** (a wrong "proceed" on a **reversible** call becomes a flagged item the user sees at the close, not a silent action) — **except** class (c), where a wrong "proceed" is not recoverable by later review.

- **STOP (blocking) — ONLY for a must-decide.** Three classes, and only these:
  - **(a) a genuine design fork** — multiple valid options, no clearly-right answer; the user's call. *e.g. "state file or derive it from the backlog?"*
  - **(b) a spec with a real trade-off to accept** — X at the cost of Y. *e.g. "the simplest fix drops the legacy format — accept that?"*
  - **(c) an irreversible / outward action** — push to a shared remote / `main`, republish/deploy, delete user content, spend, any external side-effect. **A HARD stop the FLAG path can NEVER absorb — even on a low-confidence call.** *e.g. "push this to main?" — always ask.*
- **RESEARCH, don't ask — for a FACTUAL / technical uncertainty.** A question resolvable from official / trusted sources is settled by **research (cited)**, never a stop. Stops are for *preference / judgment*, not facts you can look up.
- **FLAG (non-blocking) — for a REVERSIBLE judgment.** A should-know (a judgment call · an accepted risk · a spec deviation · a low-confidence choice) whose cost-if-wrong is **reversible**: record a **one-line flag + the chosen default** and **CONTINUE**. *e.g. "named the helper `selectItems` (spec silent); FLAG + continued."* (A low-confidence *irreversible* call is **not** a flag — it is class (c) → STOP.)
- **SURFACE all flags at the close** as **"things to review,"** read async *after* the work lands. (The running list lives in the plan's Status block as a `Flags:` sub-line — kept **distinct** from the disposition field; the close-out surfaces flags **and** dispositions as two separate concerns.)

**Acceptance:** an autonomous run completes without stopping for anything that isn't a genuine user-action; every reversible judgment is flagged with a chosen default and surfaced at the close; a factual uncertainty triggers cited research; the three blocking classes always stop.

**build-to-green (the separate who-watches axis — earned per-repo).** Running **unwatched** (`engine/build-item.js` runs the implement → gates → verify → fix loop mechanically, returning only at the retained hard stops) is **requestable**, unlocked per-repo only when CI runs the deterministic gates, a test baseline covers the touched code, and the item traces to an approved spec with testable acceptance criteria — the contract, the evidence-stated checks and the verbatim decline live in `skills/build/SKILL.md` → Mode handling. The engine runs only via the Workflow tool from the installed plugin, so the ask declines only when a per-repo condition is unmet or that engine is unavailable. Watched or unwatched, the **rules above govern when to stop** (the class-(c) hard stop is a *return* to the orchestrator in the engine case); build-to-green reduces unwatched-run risk, never a substitute for the unbuilt deterministic trust-gates.

Iterate to this **fixed** bar, then **stop** — it terminates because the bar is *finite*, not "is it perfect?". Genuinely separate future work → `ROADMAP.md` (backlog, *not* debt).

## The finder pipeline (audit · product · doctor → backlog → build)

Three **finders** surface candidate work — `audit` (engineering, vs the `docs/claugentic-standards/` modules), `product` gap-mode (vs the spec), `doctor` (harness-health) — sharing **one** lifecycle: **`FIND → SELECT → PLAN → OFFER-BUILD → BUILD`**. Nothing is planned, spec'd, or written to the backlog until the user has **chosen** it.

**FIND.** The finder sweeps and returns a **candidate list** — for `audit` / `product` the engine's structured `items`; for `doctor` its diagnose rows. The sweep's **coverage / run-report is computed over the whole scope** (every lens, every dir), independent of what the user later picks — this matters for the SELECT invariant below.

**SELECT — the scope gate.** Where the user picks what to act on, *before* anything is written to the backlog. **Model-upheld user action, not a mechanical gate.**

- **Read the dismissal memory first.** Before presenting candidates, read the rejected-memory fence (`<!-- harness-audit:rejected-findings -->` for audit, `<!-- product-critic:rejected-proposals -->` for product) and **omit any already-dismissed candidate** — a finding the user once called *wrong* stays dropped.
- **Present the remaining candidates as an editable markdown checklist** — one `- [ ]` line per candidate, **reusing the rendered backlog-item form** so it scales to N (AskUserQuestion caps at ~4). The checklist is a **transient conversational artifact** shown *before* the fence is written — **never persisted into the managed `harness-audit:backlog` / `harness-product:backlog` fence**. Items are unchecked by default.
- **The checked subset is the SELECT result.** Unchecked candidates are **dropped for this run**, not written to the backlog — the anti-bloat gate.
- **Skip ≠ reject.** A non-tick is a **per-run skip** — not recorded in the durable reject-memory, and it **may resurface** later. **Explicit rejection** ("this finding is *wrong*", not "not now") appends one terse line to the rejected-memory fence so it stays dropped across runs. SELECT *offers* that option, but a non-tick **defaults to skip, never reject** — rejection is a deliberate override, never inferred from an unchecked box.
- **Render from the selected subset via the `renderOnly` re-render seam.** The engine is a sandboxed Workflow script — a prose skill **cannot** call its internal `renderBacklogFence` on a filtered subset (un-exported, no render-only CLI entry). So the skill filters `result.items` to the ticked subset and **re-invokes the engine's agent-free `renderOnly` mode** with `{ ...result, items: selected }`; that fast-path (in `engine/audit.js`) re-renders the fence and returns the new `renderedBacklog`, keeping the renderer the **single source** of the fence format. `lensCoverage` / `verification` pass through **unchanged**. Keep-all / nothing-found skips `renderOnly` and writes the engine's original `renderedBacklog`; an **empty** selection is **never** passed to `renderOnly`.
- **★ INVARIANT — coverage / run-report stay full-scope; no empty `renderOnly` over a found run.** The `lensCoverage` and `verification` / run-report fields handed to `renderOnly` remain the **unfiltered, full-audit** values, so the fence reports honestly: *"we looked at all of this; you chose to act on these."* **Never recompute coverage over the selected subset** — that would falsely claim "every lens spoke" about only the kept findings. Because the skill narrows **only** `items`, this holds automatically — stated as an invariant so a future edit doesn't also filter those fields. **Second clause:** `renderOnly` is **never invoked with an empty `items`** when the full run carried Tier-1/2 findings — an empty re-render emits the engine's terminal "sound" signal, a **false** claim when the run found things (handle keep-none conversationally + skip the write).

**Two SELECTs at two altitudes (don't conflate them).** The **finder's** SELECT (above) gates **that finder's own fresh `result.items`** before its fence is written — per-finder, per-run. **Build-TRIAGE** is the separate, later select that assembles the *worklist* from **three sources**: the `harness-audit:backlog` candidates, the `harness-product:backlog` candidates, and the durable **Bugs** section (planless one-liners; selecting one **commits** it). The Bugs-as-source reader is wired at **build-triage**, not the finder SELECT.

**PLAN — preemptive, per committed item (architecture-first, not a stub).** When an item is **committed** (SELECTed), its **full plan file** is produced via **Stage 2** (2a → 2b → 2c → the **Stage-3 `synthesizer-gate` gate**), structured by `docs/claugentic-PLAN_TEMPLATE.md`: problem · **Architecture & holistic fit** · approach · decomposition · the finding's evidence (`file:line`), plus a one-line `ROADMAP.md` entry. Specialist-produced groundwork so build never re-derives context — but **reviewed groundwork, never a guarantee of quality**, and **model-upheld** (nothing mechanical forces a plan).

- **The deep per-slice Spec stays just-in-time.** "Preemptive PLAN" means the *plan* exists before that item is built (**architecture-first**), **not** that every slice is deep-spec'd upfront. The deep Spec is produced inside build as it reaches each slice (Stage 4) — the step-pruning gate, cheaper JIT.
- **★ Plan-volume bound (no dozens of plans at once).** **build-now** items are planned **one at a time as build works them** — the loop is serial, so at most one fresh plan file exists at a time. **backlog** items get only a **one-line fence / `ROADMAP.md` entry**, planned **just-in-time when a later `/build` reaches them**.

**OFFER-BUILD — the finder→build bridge (no dead-end).** After SELECT the finder run **continues** instead of dead-ending into a manual `/build`: it asks — a small binary moment, so via **AskUserQuestion** — *"build these now, or leave them in the backlog?"* **Default = leave in the backlog.** Build is **offered, never forced** (forced auto-build is an explicit non-goal); the offer is **model-upheld**. **Build now** → enter the build loop. **Leave** → the items persist as backlog lines for a later `/build`, their plans produced JIT then.

**BUILD (the continuing contract).** Build works selected items **one at a time**, each from its **pre-made plan if it has one** (else planned architecture-first via Stage 2 first), with the **deep per-slice Spec → Approve → Implement → Verify run just-in-time** as build reaches that slice.

**Scope approval precedes the deep per-slice Spec.** The finder's **SELECT gates *scope*** — *which items* — **before** Stage 4 ever runs, so a specialist never deep-specs a step the user will later reject. Three altitudes: **SELECT gates scope** · **Stage 4 gates steps** (which slices, JIT) · **Stage 5 approves the spec**. No code before Approval.

**Commitment, not capture, triggers the plan:** selecting an item *is* committing it *is* the Stage-2 trigger — a raw Bug / Later one-liner stays planless until selected, and a trivial item skips the backlog entirely and is just done.

## Executing an audit backlog item — tag → discipline

`/claugentic-dev-harness:audit` writes a tagged backlog into `docs/claugentic-ROADMAP.md`; there is **no separate refactor command**. Each item runs the pipeline above, and its **tag selects the discipline**. This table is the canonical home of that mapping; the rationale is settled — don't re-litigate it.

| Tag | Discipline |
|-----|-----------|
| **`refactor`** | **Characterization-tests-first — a HARD precondition.** A refactor on untested behavior-bearing code **cannot start until its Tier-1 "establish a test baseline" item is done**; absent that baseline the implementer **stops and asks**. **Model-upheld by design** — held by the implementer + the Verify gate; a mechanical `PreToolUse` hook was **declined** (0035, 2026-07-04), never a coming gate. **Say this when the pause fires:** *"Before I tidy this code I need to capture what it currently does as a test, or I can't prove I didn't change its behavior — so I'll establish that baseline first."* |
| **`capability-upgrade`** | Migration safety — feature-flag the new path · dual-write / shadow-read · keep a rollback. |
| **`dependency-health`** | Update + verify — bump, full suite green, changelog checked for breaking changes. |
| **`bug`** | Reproduce-first — a **failing test that captures the bug**, then the fix that makes it pass. *(The harness governs *fixing* a known bug; it has no *investigation* procedure for an **unknown** failure. For one whose cause you don't yet know, **consider the bundled `/debug` skill** to reproduce+isolate first, then enter the pipeline as a `bug` item. An option, never wired behavior.)* |
| **`feature`** | The standard pipeline; **test-first-when-chosen** adds an independent-test-author red-first step (**model-upheld — mechanical enforcement declined**), never a default precondition. |

### Choosing the approach for the work at hand — the methodology toolbox

Fit the approach to the **nature of the work at hand**, per work-item — **never one golden hammer**. Extends the tag→discipline table above (which picks per work-TYPE). **MODEL-UPHELD: no code reads it, and there is no mechanical selector.**

**The harness does not mandate TDD.** Red-first is already the `bug`/`refactor` discipline; for `feature` work test-first is a *when-chosen* option wired into the `implementer` prompt + the Verify gate — **model-upheld, mechanical enforcement declined by design** — never the flagship, the default, or charter-enforced. ATDD/BDD, trunk-based and CI/CD-gating are **structurally embodied** (acceptance criteria + runtime QA + the DoD gates + the land-slice-complete grain); DDD, XP, contract-first and spec-by-example are **accommodated**, never imposed. **Fit, one line each** (the *when-it-fits* rationale `docs/claugentic-CHARTER.md` and the `implementer` consult): **red-first/TDD** — logic-heavy work, well-understood requirements, any `bug`/`refactor` · **ATDD/BDD** — user-facing behavior with acceptance criteria · **DDD** — complex/rich domain logic · **contract-first** — API/integration boundaries · **spec-by-example** — concrete examples clarify intent · **XP** — rapid iteration wanting test-first + small releases · **trunk-based/CI-gating** — the default grain, always fits. **Two are opt-in *against the grain*, said out loud rather than silently half-supported:** **GitFlow** (long-lived branches fight the small-batch grain) and **Shape Up** (fixed-appetite/variable-scope fights the **fixed-quality-bar** grain — the harness fixes quality and varies scope by slicing).

## 9. The learning loop (how the harness grows)

A **finite harvest checklist run at Land** (model-upheld discipline, not automation — it does not trigger by itself). The orchestrator convenes **`retrospect-harvester`** to sweep the landed change against the six categories and return the concrete edits, then applies them (it owns the commit). The **active** counterpart to `doctor`'s **passive** *"a recent land lacks a DECISIONS / INVARIANTS / standards touch — did the harvest fire?"* flag: **doctor REPORTS the signal; `retrospect-harvester` DOES the harvest** (one owner per role, no double-build). For each category, **emit the edit** or an explicit *"nothing durable this slice"*:

- **(a)** A convention that recurred across review findings → **promote to STANDARDS / CLAUDE.md** — *harness-self*: the module **is** the source; edit it. **In an adopter** it is a managed copy: a universal lesson stages in `docs/claugentic-standards/CANDIDATES.md` → upstream; a repo-specific one goes in your `CLAUDE.md` harness area. A promoted lesson **must record the incident that motivated it** — so it is un-cargo-cultable and safe to delete once its cause is gone.
- **(b)** A manual/lens catch a gate or checklist **could have made** → **open a gate item on `ROADMAP.md`** (not just a `claugentic-DECISIONS.md` line — a logged decision doesn't become a check by itself).
- **(c)** A prompt tweak that sharpened a specialist → **fold into the `.claude/agents/` role file** — *harness-self only*; role files are **plugin-resident**, so **in an adopter** the tweak goes upstream.
- **(d)** Process friction → **edit this `WORKFLOW.md`** — *harness-self*; **in an adopter** your copy is managed (re-`init` replaces it), so a durable rule goes upstream and a repo-local one to your `CLAUDE.md` harness area.
- **(e)** Every non-trivial choice → **one dated line in `claugentic-DECISIONS.md`**.
- **(f)** A **load-bearing invariant** this slice established or relied on (a "must stay true or X breaks" constraint whose rationale isn't obvious from the code) → **record it in `docs/claugentic-INVARIANTS.md`** with its why + dated provenance. **Create the file lazily**; most slices have none, so the honest emit is usually *"no new invariant this slice."*

**The six categories name the COMMON lessons and their homes — not a closed destination list.** A lesson whose canonical home is elsewhere (the PLAYBOOK · a skill's SKILL.md · a template — all plugin-side, so from an adopter they route upstream) routes there. **One canonical home per lesson (pointers where needed, never copies)** — scattered duplicates drift into the conflicting entries the consult-DECISIONS-before-writing guard exists to prevent.

**A harvest edit landing in a SHIPPED file — plugin-side or upstream from an adopter — is written adopter-aware:** **no reference to a dev-only path an adopter's repo will never have**, and no uncaveated harness-self gate mention. Name the *thing* ("the release runbook", "the shipped-content scan"), not the stripped path. **And pick the HOME by the same test:** a lesson that binds an **adopter's** run cannot live only in a dev-only ledger that never reaches them — put the rule in the shipped surface that owns its topic and keep the dated ledger line as a **pointer**. *(2026-08-13: a harvest wrote a stripped release-runbook path into an `honesty-reviewer` bar item; the shipped-content gate caught the dangle at the next Land. The gate worked; the harvester didn't know.)*

**Promotion is two-tier (manual, user-approved):** a *universal* lesson → stage in `docs/claugentic-standards/CANDIDATES.md`, then promote upstream so every repo gets it on update (in the harness's own repo there is no staging step — the module *is* upstream); a *codebase-specific* lesson stays **local** (`CLAUDE.md` / `claugentic-DECISIONS.md`), never propagated. **Upstream is the plugin's own repo — open an issue or a pull request at `https://github.com/sh4npeiris/claugentic-dev-harness`.** Named here once — every other mention points here.

## Plan file lifecycle

`​.claude/plans/NNNN-<slug>.md` (Plan + Review + Spec + slice checklist) — one plan per substantial change; the slices inside are the per-session units. Numbering is sequential (`0001`, `0002`, …).

**Commit the plan file at draft (Stage 2), not only at Land.** An uncommitted-and-untracked plan is unrecoverable if the session crashes — and once `.claude/plans/` is emptied by a prior Land, git no longer tracks the dir, so a new plan has no safety net. Commit each plan (and each slice) promptly. *(2026-06-25, plan 0028: a draft was lost exactly this way.)*

**A plan completes — and is removed (git history keeps it) — once every remaining item has a disposition, gated *only* on the committed slice, never on deferred/rejected/blocked parts.** At close, give each still-unchecked item one of three:

- **done** — checked off (it landed).
- **defer** — a one-line item on `docs/claugentic-ROADMAP.md`; OR, for a substantial / externally-blocked remainder, **move the remaining items into a NEW plan file** (+ one roadmap line pointing to it). Either way the *current* plan closes now.
- **reject** — recorded as a declined decision (a `docs/claugentic-DECISIONS.md` line so it isn't re-proposed) and dropped.

Then the plan **completes and is deleted.** A plan **never lingers `pending` waiting on an outside event** — when the last pieces are blocked externally, defer-to-new-plan (or reject) and **close now**. (`skills/build/SKILL.md` close-out + `docs/claugentic-PLAN_TEMPLATE.md`'s Disposition note carry the same model.)

### Scope that emerges mid-build — the in-flight split

Work surfacing *while building* is **not** silently absorbed; it splits two ways (the user makes the call at plan-review / approve, or at disposition):

- **(a) intrinsic to the feature** → **fold it into the plan**: account · spec · deliver, and **re-run the steps** (plan → review → spec → build → verify). The decomposition grows because it *is* the feature — in-scope discovery, not creep.
- **(b) out-of-scope** (a defect, or unrelated work) → does **not** bloat the plan. Record it on `docs/claugentic-ROADMAP.md` (a defect → the **Bugs** section; other work → the relevant backlog) and carry on.

**There is no "tech-debt" parking section — debt is structurally prevented, not parked.** Every slice lands complete and Verify audits the diff against the in-scope standards *before* it lands, so what would become debt is built wholly instead: in-scope discovery → fold and re-run; a too-big slice → re-decompose; an emergent design flaw → re-plan + re-review; out-of-scope work → its own roadmap item and complete plan; an external blocker → deferred + tracked. *Deferring scope* (tracked, completed wholly later) is not *creating debt* (a half-done thing left in code — not allowed). **Model-upheld and reviewer-caught, not a mechanical guarantee.** *Existing* debt in an adopter codebase is the **audit's** domain.
